Where we are

  • L7: a dependency graph produced a deterministic order and useful diagnostics
  • Today the graph executes: tasks run on workers, take minutes, touch external systems, fail, get retried — and the engine itself can crash

The data structures are simple (a DAG, a map of task states, a queue, a log). The difficulty is the semantics.

Today's distinctive lesson Failure semantics and recovery behaviour matter as much as successful execution. A workflow engine is defined by what it promises when things go wrong.

The workflow

00:05

Collect answers; do not resolve yet

  1. Per task: state, attempt count, timestamps, retry schedule, outputs/artifact locations, error of the last attempt. Per workflow: run id, parameters, overall status.
  2. If state is only in memory: everything is lost; the run restarts from scratch (expensive: Train may take hours) or, worse, is forgotten. So state must be durable.

Part 2 · 00:20–01:00

DAG, ready set and the task state machine

From Lecture 7's order to a scheduler

  • The DAG is validated once (L7 resolver): no cycles, no missing tasks
  • At runtime we do not need a full order — we need the ready set: tasks whose dependencies have all succeeded
  • Kahn's queue, driven by events instead of a loop
  • Workers pull ready tasks; parallelism = size of the ready set, capped by worker slots
Key design point "Dependency finished" is not enough. Ready means every dependency is SUCCEEDED. Failed or skipped dependencies need an explicit policy.

00:20

Say

"Last week the ready set was a heap inside a loop that ran in microseconds. Today each 'pop' starts a job that may take an hour and may fail, and the heap must survive a crash. Same structure, completely different engineering."

Ask

"Should Profile wait for Train? No dependency, so no. Should Publish run if Profile fails?" Expected: depends on product semantics — here Publish depends only on Evaluate, so yes. Policies like 'fail the whole workflow on any failure' vs 'continue independent branches' are product decisions; our engine continues independent branches.

Deterministic dispatch

Our ready() returns task ids sorted (std::map). Deterministic dispatch makes failure tests reproducible — Lecture 7's point reused.

Task state machine

00:28

Walk through transitions

  • PENDING → READY: derived — all dependencies SUCCEEDED.
  • READY → RUNNING: start() assigns attempt k (1, 2, …).
  • RUNNING → SUCCEEDED / RETRYING / FAILED: driven by a message that names the attempt k.
  • RETRYING → READY: when the backoff delay has elapsed (time injected via tick(now), as in Lecture 1).
  • FAILED causes dependents → SKIPPED (transitively).
  • Terminal states never change. This is an invariant enforced by making every transition explicit.

Ask

"Why is SKIPPED a different state from FAILED?" Expected: for operators and metrics — 'this task was broken' vs 'this task never had a chance'. Alerting on FAILED only avoids 40 alerts for one root cause. Diagnosability again (L7).

Misconception

"A boolean done flag per task is enough." It cannot express retrying, skipped, cancelled, or 'unknown outcome' — and every missing state becomes an ambiguous bug later.

Retries: limits, backoff, and which failures

FailureRetry?
Network timeout, 503, worker lostYes — transient
Validation error in the dataNo — will fail again
Out of memoryMaybe, on a bigger worker
UnknownLimited retries, then FAILED

Delay before attempt k+1: base · 2^(k−1), capped, plus jitter.

Why backoff + jitter A dependency outage makes every task fail at once. Immediate, synchronised retries hit the recovering service all together — a retry storm (Lecture 3's stampede). Exponential delays spread the load; random jitter de-synchronises it.

00:36

Teaching points

  • The retry limit is an invariant: attempts ≤ max_attempts. It must survive restarts — so attempt counts are durable state, not an in-memory counter.
  • Retrying a permanent error wastes resources and delays the failure signal. Classifying errors is part of the task's contract: the task should say transient vs permanent.
  • Cap the backoff (e.g. 10 minutes); otherwise 2^k grows past the workflow's deadline.

Ask

"Our engine computes retry_at from the failure event's timestamp. Why not from 'now' at replay time?" Expected: recovery would reset every backoff after a restart, causing an immediate retry storm after an engine restart.

Propagation, skipping and cancellation

  • Permanent failure of Train → Evaluate, Publish SKIPPED; Profile continues
  • Workflow result: FAILED, with the root cause named
  • Cancel: every non-terminal task → CANCELLED; RUNNING tasks must be told to stop, and may not
  • After cancel, late completion messages must not resurrect tasks
Ask A user cancels while Publish is RUNNING and the partner API call is in flight. What is the state of the world? What should the UI say?

00:45

Expected answer

Cancellation is a request. The in-flight call may complete. The honest state is "cancel requested; outcome of Publish unknown". The UI must not claim "nothing was published". Many engines have an explicit CANCELLING state for this; ours goes straight to CANCELLED and ignores later messages, which is simpler but hides the uncertainty — name the trade-off.

Teaching point

"Every state name is a promise to the user. CANCELLED promises nothing will happen any more. Can you keep that promise? If not, the state is lying."

Transition

"That uncertainty — did the side effect happen or not? — is the central problem. Part 3."

API boundaries

class Workflow {
public:
    Workflow(std::vector<TaskSpec> specs, Journal& journal, int64_t backoff_base);
    std::vector<std::string> ready() const;                  // sorted
    int  start(const std::string& id, int64_t now);          // READY -> RUNNING, returns attempt k
    bool complete(const std::string& id, int attempt, int64_t now);
    bool fail(const std::string& id, int attempt, bool transient, int64_t now);
    void tick(int64_t now);                                  // RETRYING -> READY after backoff
    void cancel(int64_t now);
    static Workflow recover(std::vector<TaskSpec>, Journal&, int64_t now);
    bool check_invariants() const;
};

Every message carries the attempt number. Time is injected. State changes go through a journal.

00:52

Point at three design decisions

  1. Attempt number in every message — lets the engine reject a late completion from attempt 1 after attempt 2 started (a "fencing token"). Without it, two attempts can both 'succeed'.
  2. Injected time — backoff is testable without sleeping; replay is deterministic.
  3. Journal — the engine never changes state without first appending the event. Recovery = replay. The same apply() function is used live and during replay, so they cannot diverge.

Boundary question

"Does the engine execute tasks?" No: it dispatches and receives messages. Execution lives in workers. That boundary is where messages get lost, duplicated and reordered — which is why the API is message-shaped and idempotent-by-attempt.

Part 3 · 01:00–01:30

Success, then crash

The critical sequence

  1. Engine journals Started(Publish, attempt 1)
  2. Worker calls the partner API — succeeds
  3. Worker sends complete(Publish, 1)…
  4. …the engine crashes before journaling it
  5. Engine restarts, replays the journal: Publish is RUNNING, outcome unknown
Pairs · 5 min What should recovery do? Consider: re-run it · mark it failed · mark it succeeded · ask someone. What does each cost?

01:00

Expected discussion

  • Re-run: at-least-once. Safe only if Publish is idempotent. Otherwise the partner receives results twice.
  • Mark succeeded: at-most-once-ish; wrong if the worker actually crashed before calling the API — results never published, silently.
  • Mark failed and alert: honest; needs a human or a reconciliation step (query the partner: "did you receive run 42?").
  • Ask the external system: best when possible — requires an API that can answer "did operation X happen?", i.e. an idempotency key or natural key.

Do not oversimplify

There is no way for the engine alone to know. Exactly-once delivery across a crash boundary is not achievable in general; systems achieve exactly-once effects by combining at-least-once execution with idempotent operations (deduplication at the receiver). Our reference engine re-runs idempotent tasks and fails non-idempotent ones with the reason "outcome unknown" (test S7).

Delivery semantics

SemanticsMechanismRisk
At-most-onceRecord "done" before doing it; never retryLost work
At-least-onceRetry until success is recordedDuplicates
Effectively onceAt-least-once + idempotent operation (dedupe by key)Needs the receiver's cooperation
The engine chooses a delivery guarantee; each task must declare whether it is safe under it. TaskSpec::idempotent is that declaration.

Say

"Most real workflow engines are at-least-once. Their documentation tells you to make tasks idempotent. That sentence moves the hard part to you — so as a designer of tasks, you must know how."

Connect back

Lecture 1's deduplication component (RecentSet / RecentWindow) is exactly the receiver-side dedupe that makes at-least-once safe. The course is coming full circle.

Making side effects idempotent

Side effectDuplicate would…Idempotency technique
Charge a paymentCharge twiceIdempotency key = workflow run + task (not attempt)
Insert a DB rowDuplicate rowUnique natural key + upsert
Write a filePartial or corrupt file on crashWrite to a temporary name, then atomic rename
Submit a jobTwo jobs runningDeterministic job name; "create if absent"
Send an emailSecond emailUsually no key: outbox table + dedupe, or accept and document it

01:13

The attempt-number trap (test S8)

If the idempotency key includes the attempt number, every retry is a new operation to the provider → double charge. The key must identify the logical operation. Test S8 shows the safe version: the gateway sees the same key twice and charges once.

Email

SMTP has no idempotency. Options: record "sent" in the same database transaction that decides to send (outbox pattern) and have a sender deduplicate; or accept rare duplicates and say so. "We might send a duplicate email after a crash" is an acceptable, honest contract for many products — not for a legal notice.

Ask

"Which of these steps in the ML pipeline are naturally idempotent?" Download (overwrite the same file), Transform (deterministic output path), Train (writes a model version — idempotent if the version name is derived from the run id), Publish (not, unless the partner API supports keys).

Durable state, checkpoints and recovery

  • Journal first: append the event, then act. Never act on an unrecorded decision.
  • State = replay(journal). One apply() for live and replay paths.
  • Checkpoint = snapshot of state + journal position, so replay does not start from day one
  • After replay, RUNNING tasks have unknown outcome → policy per task
  • Stale messages: attempt number ≠ current → ignore and count
Order matters Journal Started(k) before dispatching attempt k. If you dispatch first and crash before journaling, recovery does not even know the task ran: attempt counts lie, and a non-idempotent task is re-run silently.

01:18

Say

"This is the write-ahead-log idea from databases, applied to orchestration. Lecture 5's index transaction log, Lecture 9's persistent structures and this journal are the same pattern: durable, append-only history from which state is derived."

Invariant

"Restart does not lose required state" becomes a testable property: for any prefix of the journal, recover(prefix) produces a state satisfying the invariants, and for a complete journal it reproduces the live state (test S9).

Real systems

Temporal/Cadence persist an event history per workflow and re-run workflow code deterministically against it; Airflow stores task-instance state in a database and treats tasks without heartbeats as failed ("zombies"). Mention as evidence that these are industry patterns, not classroom inventions.

Observability and audit

Every transition should be visible

  • Who/what/when: task, attempt, worker, timestamps, error
  • Counters: retries, ignored stale messages, skipped tasks, unknown outcomes
  • Durations per task and attempt; queue wait vs run time
The journal is the audit log "Why did Publish run twice on 3 March?" should be answerable from the journal alone: Started(1), crash, recovery, Started(2), Succeeded(2) — and the idempotency key both used.

Part 5 · 02:20–02:45

Validation: invariants and failure injection

Invariants of a workflow engine

  1. A task is READY, RUNNING, RETRYING or SUCCEEDED only if all its dependencies SUCCEEDED
  2. A PENDING task has at least one dependency not yet SUCCEEDED (promotion is never forgotten)
  3. SKIPPED only if some dependency FAILED, SKIPPED or CANCELLED
  4. 0 ≤ attempts ≤ max_attempts; RUNNING implies attempts ≥ 1
  5. Terminal states never change
  6. recover(journal) reproduces the live state
How they are checked
  • 1–4: check_invariants() after every step of every scenario
  • 5: all transitions go through apply(); messages for terminal tasks are ignored
  • 6: replay test (S9) and crash tests (S6–S8)

02:20

Ask

"Which invariant would catch 'task started before its dependency succeeded'?" #1. "Which bug would violate #2?" Forgetting to call promote() after a replayed success — the workflow hangs forever with nothing READY and nothing RUNNING. A hang is the hardest failure to notice; the invariant turns it into a test failure.

Extension

A stronger test: generate random fault sequences (fail/succeed/duplicate/crash at random points), call check_invariants() after each, and after a crash compare recovered state with an independent model. This is property-based testing applied to a state machine.

Teaching point: measurement is not only nanoseconds

How to simulate a crash in a unit test

Let the Workflow object go out of scope (all in-memory state lost) and keep only the Journal — the durable part. Then call recover. This is cheap, deterministic crash testing. Real systems add process-kill tests and chaos testing in staging.

Summary

  1. A workflow engine is a DAG plus a durable state machine per task; the ready set drives scheduling.
  2. Explicit states (RETRYING, SKIPPED, CANCELLED) make failure behaviour specifiable and observable.
  3. Retries need limits, error classification, exponential backoff and jitter.
  4. After a crash, a running task's outcome is unknown; idempotency decides whether re-running is safe.
  5. Journal before acting; derive state by replay; fence messages with attempt numbers.
  6. Validate with invariants and injected faults: evidence is not only nanoseconds.
