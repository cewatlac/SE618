Workflow Engines, DAGs, Failure and Recovery

Anyone can run a DAG when nothing fails. The engineering is in what happens when something does.

Where we are

  • L7: a dependency graph produced a deterministic order and useful diagnostics
  • Today the graph executes: tasks run on workers, take minutes, touch external systems, fail, get retried — and the engine itself can crash

The data structures are simple (a DAG, a map of task states, a queue, a log). The difficulty is the semantics.

Today's distinctive lesson Failure semantics and recovery behaviour matter as much as successful execution. A workflow engine is defined by what it promises when things go wrong.

Part 2 · 00:20–01:00

DAG, ready set and the task state machine

From Lecture 7's order to a scheduler

  • The DAG is validated once (L7 resolver): no cycles, no missing tasks
  • At runtime we do not need a full order — we need the ready set: tasks whose dependencies have all succeeded
  • Kahn's queue, driven by events instead of a loop
  • Workers pull ready tasks; parallelism = size of the ready set, capped by worker slots
Key design point "Dependency finished" is not enough. Ready means every dependency is SUCCEEDED. Failed or skipped dependencies need an explicit policy.

Task state machine

Retries: limits, backoff, and which failures

FailureRetry?
Network timeout, 503, worker lostYes — transient
Validation error in the dataNo — will fail again
Out of memoryMaybe, on a bigger worker
UnknownLimited retries, then FAILED

Delay before attempt k+1: base · 2^(k−1), capped, plus jitter.

Why backoff + jitter A dependency outage makes every task fail at once. Immediate, synchronised retries hit the recovering service all together — a retry storm (Lecture 3's stampede). Exponential delays spread the load; random jitter de-synchronises it.

Propagation, skipping and cancellation

  • Permanent failure of Train → Evaluate, Publish SKIPPED; Profile continues
  • Workflow result: FAILED, with the root cause named
  • Cancel: every non-terminal task → CANCELLED; RUNNING tasks must be told to stop, and may not
  • After cancel, late completion messages must not resurrect tasks
Ask A user cancels while Publish is RUNNING and the partner API call is in flight. What is the state of the world? What should the UI say?

API boundaries

class Workflow {
public:
    Workflow(std::vector<TaskSpec> specs, Journal& journal, int64_t backoff_base);
    std::vector<std::string> ready() const;                  // sorted
    int  start(const std::string& id, int64_t now);          // READY -> RUNNING, returns attempt k
    bool complete(const std::string& id, int attempt, int64_t now);
    bool fail(const std::string& id, int attempt, bool transient, int64_t now);
    void tick(int64_t now);                                  // RETRYING -> READY after backoff
    void cancel(int64_t now);
    static Workflow recover(std::vector<TaskSpec>, Journal&, int64_t now);
    bool check_invariants() const;
};

Every message carries the attempt number. Time is injected. State changes go through a journal.

Part 3 · 01:00–01:30

Success, then crash

The critical sequence

  1. Engine journals Started(Publish, attempt 1)
  2. Worker calls the partner API — succeeds
  3. Worker sends complete(Publish, 1)…
  4. …the engine crashes before journaling it
  5. Engine restarts, replays the journal: Publish is RUNNING, outcome unknown
Pairs · 5 min What should recovery do? Consider: re-run it · mark it failed · mark it succeeded · ask someone. What does each cost?

Delivery semantics

SemanticsMechanismRisk
At-most-onceRecord "done" before doing it; never retryLost work
At-least-onceRetry until success is recordedDuplicates
Effectively onceAt-least-once + idempotent operation (dedupe by key)Needs the receiver's cooperation
The engine chooses a delivery guarantee; each task must declare whether it is safe under it. TaskSpec::idempotent is that declaration.

Making side effects idempotent

Side effectDuplicate would…Idempotency technique
Charge a paymentCharge twiceIdempotency key = workflow run + task (not attempt)
Insert a DB rowDuplicate rowUnique natural key + upsert
Write a filePartial or corrupt file on crashWrite to a temporary name, then atomic rename
Submit a jobTwo jobs runningDeterministic job name; "create if absent"
Send an emailSecond emailUsually no key: outbox table + dedupe, or accept and document it

Durable state, checkpoints and recovery

  • Journal first: append the event, then act. Never act on an unrecorded decision.
  • State = replay(journal). One apply() for live and replay paths.
  • Checkpoint = snapshot of state + journal position, so replay does not start from day one
  • After replay, RUNNING tasks have unknown outcome → policy per task
  • Stale messages: attempt number ≠ current → ignore and count
Order matters Journal Started(k) before dispatching attempt k. If you dispatch first and crash before journaling, recovery does not even know the task ran: attempt counts lie, and a non-idempotent task is re-run silently.

Observability and audit

Every transition should be visible

  • Who/what/when: task, attempt, worker, timestamps, error
  • Counters: retries, ignored stale messages, skipped tasks, unknown outcomes
  • Durations per task and attempt; queue wait vs run time
The journal is the audit log "Why did Publish run twice on 3 March?" should be answerable from the journal alone: Started(1), crash, recovery, Started(2), Succeeded(2) — and the idempotency key both used.

Part 5 · 02:20–02:45

Validation: invariants and failure injection

Invariants of a workflow engine

  1. A task is READY, RUNNING, RETRYING or SUCCEEDED only if all its dependencies SUCCEEDED
  2. A PENDING task has at least one dependency not yet SUCCEEDED (promotion is never forgotten)
  3. SKIPPED only if some dependency FAILED, SKIPPED or CANCELLED
  4. 0 ≤ attempts ≤ max_attempts; RUNNING implies attempts ≥ 1
  5. Terminal states never change
  6. recover(journal) reproduces the live state
How they are checked
  • 1–4: check_invariants() after every step of every scenario
  • 5: all transitions go through apply(); messages for terminal tasks are ignored
  • 6: replay test (S9) and crash tests (S6–S8)

Summary

  1. A workflow engine is a DAG plus a durable state machine per task; the ready set drives scheduling.
  2. Explicit states (RETRYING, SKIPPED, CANCELLED) make failure behaviour specifiable and observable.
  3. Retries need limits, error classification, exponential backoff and jitter.
  4. After a crash, a running task's outcome is unknown; idempotency decides whether re-running is safe.
  5. Journal before acting; derive state by replay; fence messages with attempt numbers.
  6. Validate with invariants and injected faults: evidence is not only nanoseconds.
