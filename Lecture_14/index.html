Round 1 — memory

Memory is abundant

What becomes acceptable that was not?

Memory is tight (10× less)

What must change first, and what do you give up?

Apply to: dedup of event IDs · autocomplete · config history · cache capacity

B 00:06

Draw out

  • Abundant: full copies for history (O(1) reads), cached top-k per trie node, exact sets, padding against false sharing. Simplicity becomes affordable.
  • Tight: binary keys instead of strings (L1: 3.6 → 1.7 GB), flat layouts instead of node-based maps (L2), sorted arrays instead of pointer tries (L4, 6× less), deltas/structural sharing for history (L9), probabilistic filters in front of exact stores (L10), compression.
  • What you give up: read speed of old versions, exactness (with a fallback), code simplicity.

Ask each group: "Which of your two designs survives a 10× memory cut unchanged?"

Round 2 — reads vs writes

Reads dominate (99%)

How much would you precompute?

Writes become frequent (50%+)

Which precomputation now hurts?

Apply to: search index · range analytics · autocomplete ranking · caches

B 00:14

Draw out

  • Read-heavy: indexes, prefix sums, cached top-k, materialised views — pay on write, collect on read (L5, L6, L4).
  • Write-heavy: prefix sums become O(n) per update (L6, 89 µs/op in the benchmark); in-place index updates amplify (L5); switch to Fenwick/segment trees, buffered/segment-based indexing with a refresh interval, or recompute lazily.
  • The general principle: every index or precomputation is a bet on the read/write ratio.

Round 3 — mutability and history

Data becomes immutable

What gets simpler? What can you precompute now?

Every historical version must stay accessible

What does that cost, and who deletes anything?

Apply to: analytics history · configuration · search segments · workflow state

B 00:22

Draw out

  • Immutable: prefix sums / sparse tables (O(1) queries), sorted arrays, compressed static structures (FSTs), lock-free readers with atomic pointer swap (L6, L4, L9, L11).
  • History required: structural sharing or deltas + checkpoints; reclamation and compaction become first-class operations; retention is a product and legal decision; snapshot tests must check old versions after new commits (L9).
  • Split by mutability (L6's hybrid, L5's segments): immutable bulk + small mutable part — a pattern that keeps recurring.

Round 4 — exactness, concurrency, skew, consistency

If…Then ask…
Exact answers are no longer requiredWhich error is harmless? What does one error cost? Can an exact store stay behind it?
Concurrency rises to 32 workersWhat is shared? Which compound operations must be atomic? Where is the hot cache line?
Key popularity becomes skewedWhich policy or sharding assumption breaks? (LRU vs LFU, hot shard)
Update consistency becomes strictWhich asynchronous or eventually consistent parts must become synchronous — at what latency cost?

B 00:30

Draw out, one per row

  • Approximate: Bloom filters before databases, Count-Min for heavy hitters; never for irreversible or security decisions (L10).
  • Concurrency: global lock degrades, sharding scales only for uniform keys, atomic APIs, immutability for readers, false sharing (L11).
  • Skew: LFU vs LRU vs scan-resistant policies (L3), hot-key sharding failure (L11), Zipf in benchmarks (L12).
  • Strict consistency: search indexes refreshed synchronously (slow writes), workflow journals written before acting, snapshot commit validation (L5, L8, L9).

Ask groups to revise one of their two initial designs under a row of their choice.

What stayed constant

Across every round, the design was conditional on:

  • the workload
  • the constraints
  • the guarantees required
  • the acceptable failures and errors
  • the evidence available
The course in one sentence There is no universally best data structure — only a decision that is justified for a stated workload, under stated constraints, supported by evidence, with its limits written down.

B 00:40

Ask: "Name one design this semester that was best in one experiment and worst in another." Expected: FlatMap (random vs strided keys, L2), LFU (Zipf vs shifting, L3), trie with cached top-k (fastest queries, most memory, L4), segment tree (dynamic vs static, L6), path copying (tiny vs bulk changes, L9), sharding (uniform vs hot key, L11).

A reusable decision framework

  1. Define the real problem
  2. Quantify the workload
  3. Identify operations
  4. Identify constraints
  5. State guarantees
  6. Define acceptable failures/errors
  7. Generate candidate designs
  1. Define API and contracts
  2. Define invariants
  3. Implement the simplest credible baseline
  4. Test correctness
  5. Form hypotheses
  6. Design fair experiments
  1. Measure
  2. Profile if needed
  3. Interpret evidence
  4. State limitations
  5. Choose
  6. Revisit when assumptions change

B 00:48

Say: "This is what SE618 was about. The structures were examples. The framework is what you keep. Step 10 — the simplest credible baseline — is the step most engineers skip, and it is the one that made most of our experiments meaningful."

How to write a strong answer

assumptionsdesign choicewhyalternativetrade-offevidence neededlimitation
"Given 95% reads, infrequent updates and sufficient memory, I would choose X because … If the workload changed to frequent updates, Y would become more attractive because … I would validate this by measuring … under … This conclusion assumes …"
"Use a segment tree because it is O(log n)." · "Bloom filters are unreliable." · "B is faster." — no workload, no condition, no evidence.

C 00:08

Say: "An answer that names the right structure without conditions earns little. An answer that names a reasonable structure, states its assumptions, and says when it would change earns most of the marks — even if the examiner had another structure in mind."

Missing information in a scenario is often intentional: state the assumption and continue.

Practice 1 — a Bloom filter at 3× capacity

A Bloom filter in front of a database was planned for 10 million keys at 1% false positives. It now holds 30 million keys.

  1. Estimate what happened to the false-positive rate. Why is the change not linear?
  2. What does the database experience?
  3. What should have been monitored? What are your options now?
Individually · 6 min, in writingUse the answer pattern. Then compare with a neighbour.

C 00:14

Let students write before discussing. Key points (full reasoning in Instructor_Only/Lecture_14/Practice_Case_Model_Reasoning.md, P3): first, the exact new rate cannot be determined from the target rate and planned n alone unless the deployed m and k are known — reward students who say so. Assuming a near-optimal design for 10M at 1%: k = 7, m ≈ 96 Mbit; at 30M, fill ≈ 0.89 → p ≈ 0.89⁷ ≈ 44%; the database sees ~44× more wasted lookups; monitor fill ratio and observed false positives; rebuild larger, scalable/partitioned filters.

Reward: an estimate with the mechanism (fill^k), a system consequence in units the operator understands, and a monitoring proposal. A vague "it gets worse" is weak.

Practice 2 — success, crash, retry

A workflow task sends an invoice through an external API. The call succeeded, but the engine crashed before recording success. After recovery, the task ran again.

  1. What went wrong? Which states and events were involved?
  2. Propose two ways to prevent a duplicate invoice, and their costs.
  3. Which tests would have caught this before production?
Pairs · 8 minWrite the state sequence first.

C 00:24

Key points (P7 in the model-reasoning file): journal had Started but not Succeeded; recovery treated the task as idempotent (at-least-once). Fixes: idempotency key per workflow run + task (not per attempt); mark non-idempotent tasks and reconcile instead of re-running; outbox. Tests: crash injection between side effect and journal write; duplicate completion; replay.

Reward answers that name the assumption that failed (idempotency), not just the bug.

Practice 3 — a "5× faster" claim

A pull request claims "the new parser is 5× faster", based on one run on the developer's laptop, compared with numbers recorded last month.

  1. What can be concluded?
  2. List the threats to validity.
  3. Design the experiment you would accept as evidence.
Groups · 8 minSeparate RESULT, INTERPRETATION and GENERALISATION.

C 00:34

Key points (P5): nothing about the parser; confounders (dates, machine state, inputs, flags), one sample, no spread, no correctness check. Accepted experiment: same machine/flags/inputs, warm-up, interleaved repetitions, median + interval + p99, memory, identical-output check, raw data and environment; plus what it still would not show. Remind: an interval does not remove systematic bias.
