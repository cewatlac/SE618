Part 1 · 01:40–01:50

A deploy blocked at 02:00

The incident

A platform starts ~400 internal services in dependency order (config → secrets → database proxies → caches → APIs → gateways). The order comes from a resolver over service manifests.

After a merge, the nightly deploy fails with:

ERROR: cycle detected

The on-call engineer has 400 manifests, 1,900 edges, and no idea where to look. Also, last week's deploy started services in a different order than the week before, although nothing changed.

Ask List everything the resolver should have told the engineer. What would make the order change between runs?

01:42

Expected answers

  • Which services are on the cycle, in order: auth-api → session-cache → auth-api.
  • Which edge was added recently (the manifest file and line that declared it).
  • Which services could still be started (partial result) — maybe 390 of 400 are fine.
  • Other problems in the same run: a dependency on a service that does not exist, a service that depends on itself.
  • Order changes: iteration over a hash map/set, parallel discovery of manifests, file-system listing order — all "unspecified" orders leaking into output.

Teaching point

"The algorithm was correct. The product failed twice: it was not diagnosable and not deterministic. Both are properties we can specify, test and implement."

Part 2 · 01:50–02:10

Representation, algorithm, determinism

Representation: what the graph must carry

  • Adjacency list name → deps: what does X need?
  • Reverse edges name → dependents: who is affected if X changes or fails? (Kahn needs them; so does impact analysis)
  • Node metadata: declared where (file, line), version, owner
  • Edge metadata: why (runtime / build / optional), version constraint
Rule of thumb Store what the error message will need. A cycle report without file/line provenance sends the engineer back to grep.

01:50

Say

"Representation is chosen for the operations — and diagnostics are operations. If you will ever print 'declared in services/auth/manifest.yaml:14', you must keep that data from parsing onwards."

Ask

"Which queries does a deployment tool need besides an order?" Expected: 'what depends on X' (reverse edges, for restarts and blast radius), 'why is X in the build' (a path from a root to X), 'what changed since last run' (diff of stable outputs — needs determinism).

Duplicate edges

Manifests often list a dependency twice (copy-paste, merge). Harmless for correctness if deduplicated, but it inflates in-degree counts in Kahn if not — a real bug source. Treat it as a warning, not an error.

Kahn vs DFS, as engineering choices

PropertyKahn (in-degree queue)DFS (post-order)
Deterministic orderEasy: a min-heap of ready namesDepends on visit order; must sort roots and neighbours
Partial result on errorNatural: everything emitted is validMust be assembled separately
Cycle pathNot directly; leftover nodes = cycles + downstreamNatural: the recursion stack holds the path
Parallel schedulingThe ready set = what can run now (L8)Not directly
Stack depthIterativeRecursion depth = longest chain (risk)
Production answer: Kahn for the order, DFS on the leftovers for the explanation.

01:57

Say

"Same asymptotic cost, O(V + E). The difference is in engineering properties. Kahn gives you determinism, partial results and the ready set for free; DFS gives you the cycle path. So use both: that is exactly what the reference solution does."

Leftover nodes

After Kahn stops, unemitted nodes are either on a cycle or downstream of one (or downstream of a missing dependency). Reporting all leftovers as 'the cycle' is a common and confusing bug: 3 services on a cycle plus 40 downstream look like a 43-node cycle. Run DFS restricted to the leftovers to extract the actual cycles.

Recursion depth

A chain of 100,000 packages (generated code, long migration chains) overflows a recursive DFS on a default 1 MB stack. Iterative DFS or Kahn avoids it. Mention; do not dwell.

Deterministic ordering is a requirement

Many valid topological orders exist. Pick one, by rule:

std::priority_queue<std::string,
    std::vector<std::string>,
    std::greater<>> ready;       // smallest name first
for (auto& [n, w] : waiting)       // std::map: sorted
    if (w == 0) ready.push(n);
while (!ready.empty()) {
    auto n = ready.top(); ready.pop();
    order.push_back(n);
    for (auto& m : dependents[n])
        if (--waiting[m] == 0) ready.push(m);
}
Why it matters
  • Reproducible builds and cache keys
  • Diffable output: "what changed since yesterday?"
  • Debuggable: a failure can be replayed
  • Tests can assert exact output
Cost: O(log V) per node for the heap. Tie-break rule becomes part of the contract.

02:03

Sources of nondeterminism to name

unordered_map/unordered_set iteration (depends on insertion order, bucket count, library version, and in some languages on a per-process random seed); directory listing order; parallel discovery; pointer addresses used as keys. Our naive resolver iterates an unordered_map: the test that shuffles the input catches it.

Ask

"Lexicographic is one rule. What else could be a sensible tie-break?" Expected: declaration order (stable with respect to input — but then input order matters); priority/criticality; 'shortest first'. Any rule is fine if it is specified and does not depend on incidental state.

Part 3 · 02:10–02:25

Diagnostics and the API

Correct vs useful

Algorithmically correct 
ERROR: cycle detected
Operationally useful 
ERROR dependency cycle:
  auth-api -> session-cache -> auth-api
  auth-api      declared services/auth.yaml:14
  session-cache declared services/cache.yaml:9
ERROR 'jobs' depends on unknown package 'queue'
WARN  'api' lists 'db' more than once (ignored)
Resolved 391 of 400 services; 9 blocked (listed)

Useful diagnostics are: specific (the path), located (file/line), complete (all problems in one run), stable (same order every time), machine-readable (a kind code, not only text).

02:10

Say

"Compare the time-to-fix. Left: the engineer bisects commits for an hour. Right: open two files, remove one line. Diagnosability is measured in operator minutes — that is a legitimate engineering metric."

'Complete' matters

A resolver that stops at the first error forces a fix-rerun loop: fix the cycle, rerun, discover the missing package, fix, rerun… Report all independent problems in one run.

Machine-readable

CI systems and IDEs want {kind: Cycle, path: [...]}, not a string to regex. Our Diagnostic has a kind, a node, a path and a message.

AskIs a broken manifest an exceptional situation for a dependency resolver?

02:16

Expected answer

No. Invalid dependency data is the normal input the resolver exists to check (Lecture 1's heuristic: expected outcomes via return values; exceptions for conditions the caller cannot handle locally). Exceptions remain right for programmer errors (e.g. a null graph) and resource failures.

The contract in resolver.hpp

  1. Dependencies before dependents.
  2. Deterministic: smallest ready name first; independent of input order.
  3. ok == false iff any error; duplicate dependency is a warning.
  4. Partial result: every package whose dependencies all resolve.
  5. Cycle path starts at the smallest name on the cycle, e.g. a → b → c → a.
  6. Diagnostics sorted by (kind, node).

Point 3 prevents the "silent partial result" problem: a caller that ignores diagnostics still sees ok == false. [[nodiscard]] on the result type would make ignoring it a compiler warning.

Invalid graph states and their classification

StateError or warning?Blocks
Missing dependency · self-dependency · cycle · duplicate package declarationErrorThat package and everything downstream
Duplicate dependencyWarningNothing (deduplicate)

02:21

Discuss the classification

  • Duplicate package declaration: why an error? Two manifests both define "auth-api" with different dependencies. Silently merging (what the naive resolver does) or picking one hides a real configuration conflict.
  • Missing dependency: some systems treat it as a warning when the dependency is optional. That requires edge metadata (optional vs required) — the representation slide again.
  • Everything else in the graph continues to resolve: partial results.

Transition

"You now have the contract. The exercise: decide the exact output for a messy input, then make the naive resolver honour the contract."

Realistic expectation (important)

Students have just finished a 90-minute exam. In ~17 minutes of coding, expect only a meaningful subset: (1) deterministic ordering (replace hash-map iteration with a min-heap/sorted container — makes test 2 pass); (2) the missing-dependency diagnostic with its path (test 3, partially); (3) one more diagnostic (self-dependency is the easiest) if time allows. Cycle-path extraction and partial results are continuation work. Say this explicitly at the start of Part B so nobody feels they failed. The full suite stays as after-class practice; discuss the reference solution next week or post it after class.

Implementation hints (give progressively)

  1. Use std::map/std::set for everything that is iterated.
  2. Validate first (duplicates, self, missing) and mark blocked packages.
  3. Kahn with a min-heap over non-blocked packages.
  4. DFS over the leftovers only; rotate the cycle to start at its smallest name.

Debrief and project connection

Debrief

  • Which test failed first on the naive resolver? (Usually: shuffled input → different order.)
  • How did you test "deterministic"? One run cannot show it: shuffle, repeat, compare.
  • Where did you put the tie-break rule — code, docs, tests? It must be all three.
For your project
  • Is any output of yours order-dependent on a hash container?
  • What is your worst error message today? Rewrite it with a path and a location.
  • Which invalid inputs do you return as diagnostics, and which do you throw on?
