Part 1 · 01:40–01:50

A deploy blocked at 02:00

The incident

A platform starts ~400 internal services in dependency order (config → secrets → database proxies → caches → APIs → gateways). The order comes from a resolver over service manifests.

After a merge, the nightly deploy fails with:

ERROR: cycle detected

The on-call engineer has 400 manifests, 1,900 edges, and no idea where to look. Also, last week's deploy started services in a different order than the week before, although nothing changed.

Ask List everything the resolver should have told the engineer. What would make the order change between runs?
Part 2 · 01:50–02:10

Representation, algorithm, determinism

Representation: what the graph must carry

  • Adjacency list name → deps: what does X need?
  • Reverse edges name → dependents: who is affected if X changes or fails? (Kahn needs them; so does impact analysis)
  • Node metadata: declared where (file, line), version, owner
  • Edge metadata: why (runtime / build / optional), version constraint
Rule of thumb Store what the error message will need. A cycle report without file/line provenance sends the engineer back to grep.

Kahn vs DFS, as engineering choices

PropertyKahn (in-degree queue)DFS (post-order)
Deterministic orderEasy: a min-heap of ready namesDepends on visit order; must sort roots and neighbours
Partial result on errorNatural: everything emitted is validMust be assembled separately
Cycle pathNot directly; leftover nodes = cycles + downstreamNatural: the recursion stack holds the path
Parallel schedulingThe ready set = what can run now (L8)Not directly
Stack depthIterativeRecursion depth = longest chain (risk)
Production answer: Kahn for the order, DFS on the leftovers for the explanation.

Deterministic ordering is a requirement

Many valid topological orders exist. Pick one, by rule:

std::priority_queue<std::string,
    std::vector<std::string>,
    std::greater<>> ready;       // smallest name first
for (auto& [n, w] : waiting)       // std::map: sorted
    if (w == 0) ready.push(n);
while (!ready.empty()) {
    auto n = ready.top(); ready.pop();
    order.push_back(n);
    for (auto& m : dependents[n])
        if (--waiting[m] == 0) ready.push(m);
}
Why it matters
  • Reproducible builds and cache keys
  • Diffable output: "what changed since yesterday?"
  • Debuggable: a failure can be replayed
  • Tests can assert exact output
Cost: O(log V) per node for the heap. Tie-break rule becomes part of the contract.
Part 3 · 02:10–02:25

Diagnostics and the API

Correct vs useful

Algorithmically correct 
ERROR: cycle detected
Operationally useful 
ERROR dependency cycle:
  auth-api -> session-cache -> auth-api
  auth-api      declared services/auth.yaml:14
  session-cache declared services/cache.yaml:9
ERROR 'jobs' depends on unknown package 'queue'
WARN  'api' lists 'db' more than once (ignored)
Resolved 391 of 400 services; 9 blocked (listed)

Useful diagnostics are: specific (the path), located (file/line), complete (all problems in one run), stable (same order every time), machine-readable (a kind code, not only text).

After class: make all of resolver_test.cpp pass. Useful for any project with a graph.

Part 5 · 02:50–03:00

Debrief and project connection

Debrief

  • Which test failed first on the naive resolver? (Usually: shuffled input → different order.)
  • How did you test "deterministic"? One run cannot show it: shuffle, repeat, compare.
  • Where did you put the tie-break rule — code, docs, tests? It must be all three.
For your project
  • Is any output of yours order-dependent on a hash container?
  • What is your worst error message today? Rewrite it with a path and a location.
  • Which invalid inputs do you return as diagnostics, and which do you throw on?
