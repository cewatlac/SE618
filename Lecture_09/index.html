Part 1 · 00:00–00:20

Scenario: configuration
with a memory

The scenario

A platform stores 20,000 settings (feature flags, limits, endpoints) read by 3,000 services.

  • ~2,000 commits/day, usually 1–5 settings each; occasionally a bulk migration changes 30%
  • Services read the current version ~50,000 times/s
  • Incident reviews ask: "what exactly was live at 14:02?"
  • Staged rollout: a branch of the config for 5% of traffic
  • Instant rollback to any version from the last 30 days; audit for 1 year
Pairs · 4 min Before any structure: which questions about versions must you answer?

00:03

Expected questions (write on the board)

  • Do we need every version, or every version for 30 days and daily snapshots after?
  • Write rate vs read rate; and which versions are read — current (hot) vs historical (rare but must be possible).
  • How big is a typical change relative to the whole state?
  • How long must versions live, and who may delete them (legal hold, audit)?
  • What does rollback mean: a new version equal to an old one (history preserved) or rewinding (history lost)?
  • Consistency: a service must see one whole version, never half of a commit.
  • Where do versions live after a restart — memory, disk, both?

Teaching point

"Rollback = create a new version equal to an old one" is the immutable answer and it keeps the audit trail intact. "Rollback = overwrite" loses exactly the evidence the incident review needs. The data model decides whether that is even possible.

Quick estimate to do aloud

20,000 settings × ~64 bytes ≈ 1.3 MB per full copy. 2,000 commits/day × 365 = 730,000 versions/year → full copies ≈ 930 GB/year. Deltas of ~3 settings ≈ 200 bytes each → ~150 MB/year. Four orders of magnitude from one representation choice.

Part 2 · 00:20–01:00

Snapshots, sharing, and
the shape of history

Mutable vs immutable state

Mutable (update in place)

  • One current state; history is gone or lives elsewhere (logs)
  • Readers and writers need coordination
  • "What did it look like at 14:02?" needs extra machinery
  • Cheapest memory; simplest hot path

Immutable versions

  • A commit creates a new version; old ones never change
  • A reader holding version v sees a stable snapshot, lock-free
  • Rollback, audit, diff, time travel become simple lookups
  • Cost: every version must be stored, shared or reclaimed
Snapshot semanticsget(v, key) returns the same answer forever, whatever happens after v was created — until v is explicitly released.

00:20

Concurrency benefit (preview of L11)

A service thread grabs the pointer to the current version and uses it for the whole request. A writer builds a new version and atomically swaps the "current" pointer. Readers never block and never see half a commit. This is read-copy-update (RCU) and the core of MVCC. It is the best argument for immutability in systems — and it only works if old versions are truly never modified (today's bug).

Misconception

"Immutable means slow because everything is copied." Only a naive implementation copies everything. The rest of Part 2 is about not copying.

00:26

Say

"Three points on a trade-off curve between write cost, read cost and memory. The benchmark later puts numbers on each cell, and at least one of them will surprise you."

Hint of the surprise

"c · log N" assumes changes are few and clustered. A change touching 30% of slots scattered randomly touches nearly every leaf — path copying then copies almost everything and pays pointer overhead. Ask the room to predict which row breaks under a bulk migration.

Structural sharing: copy only the path

00:32

Explain

A commit copies the nodes on the path from the root to each changed leaf (O(log N) per change) and points the copies at the untouched subtrees of the old version. Both versions are complete trees; they simply share most nodes. This is how Clojure's persistent vectors (32-way tries), Scala's immutable collections and Git's tree objects work.

Our implementation

A 32-ary radix tree over N slots: depth ⌈log₃₂ N⌉ (3 levels for 16,384 slots). Nodes are shared_ptr<const Node>: the const is the promise that shared nodes are never mutated, and the reference count reclaims nodes once no version uses them.

Ask

"How many nodes does version 8 cost if the change touches slots 5 and 6, which sit in the same leaf? And slots 5 and 9,000?" Expected: 3 (same path) vs ~5 (two paths share only the root) — the cost depends on clustering, which depends on the workload.

Copy-on-write: sharing until someone writes

  • Share a buffer/page/object between owners; copy only when one of them writes
  • Examples: fork() memory pages, VM/container image layers, ZFS/Btrfs snapshots, Qt implicitly shared containers
  • Decision rule: "am I the only owner?" → write in place; else copy first
The classic trap "Only owner" must mean nobody can observe this data — not "nobody is likely to", not "only the newest version". A shared pointer's use count can be 1 while a parent node that points to it is shared by two versions.

00:38

Say

"Copy-on-write is structural sharing's lazy cousin. Its correctness rests entirely on one question: is this object observable by anyone else? Getting that question wrong is the most common bug in persistent structures — and today's lab contains a version of it."

Concurrency caution

std::string used copy-on-write in pre-C++11 libstdc++; it was removed because the reference count made COW strings expensive and error-prone under threads. Sharing always needs an ownership story that holds under concurrency.

Versions form a graph

  • Version id = stable name for an immutable state
  • Linear history: undo stacks, audit logs
  • Branches: staged rollouts, experiments, drafts
  • Merges need a policy for conflicts (not today)
  • Ids: sequential numbers (need a coordinator) or content hashes (Git: same content → same id, deduplication for free)

00:43

Lifecycle question to plant

"If v3 is older than 30 days, can we delete it?" With full copies: yes. With deltas: v4 and v5 are stored as changes relative to v3 — deleting v3's delta breaks them. With structural sharing: v3's unique nodes are freed, shared ones survive. The version graph turns "delete" into a dependency problem (Lecture 7 again).

Content addressing

Git names objects by the hash of their content: identical subtrees are automatically shared across commits and branches, and integrity is checkable. Cost: hashing on every write and ids that are not ordered in time.

AskA photo editor applies a blur to a 50 MB image. Which model would you use for its undo, and why not the others?

00:50

Expected answer

Blur is not invertible: a command log would need to store the original pixels anyway. Full snapshots of 50 MB per step exhaust memory after ~20 steps. Practical answer: tile the image and snapshot only the tiles an operation touches (structural sharing at tile granularity) — or store the "before" tiles as a reverse delta. Text editors typically use command logs (inserts and deletes are cheap to invert) or piece tables.

Teaching point

The right undo model depends on operation invertibility and change size — i.e. on the workload, again.

Part 3 · 01:00–01:30

Lifecycle: ownership, reclamation,
compaction, disks and crashes

Who owns an old version?

  • A reader holding version v must be able to finish, even if v is "deleted" meanwhile
  • Reference counting (shared_ptr): a node is freed when its last owner goes — deterministic, but costs an atomic operation per copy and cannot free cycles
  • Tracing GC (JVM, Git gc): free what is unreachable from live roots — batch cost, pauses
  • Epochs / leases: free after all readers of an epoch have left (RCU)
Invariant A released or compacted version is never readable by accident: either get fails with a clear error, or the data is still valid for readers who held it.

01:00

Say

"Immutability doesn't remove the lifetime problem; it moves it. Instead of 'who may write this?' you ask 'who may still read this?'. In C++ that question is yours to answer; in a GC language the runtime answers it — at a cost."

Our stores

  • Full copy and path copy: release(v) drops a root; shared_ptr frees whatever is no longer shared.
  • Delta chain: a version whose children still depend on it cannot be freed on its own. release refuses; retire marks it unneeded; compact materialises a descendant and reclaims retired ancestors.

Dangling handles

Version ids are plain integers in our API. After release, get throws out_of_range. Returning references into a version would dangle after release — the Lecture 1 lesson, applied to history.

Compaction and memory amplification

  • Amplification = bytes stored ÷ bytes of live, useful state
  • Sources: many versions, per-node pointer overhead, partially shared nodes, fragmentation
  • Compaction: rewrite history into a smaller form
    • materialise a checkpoint, drop the chain before it
    • thin old versions (keep one per day after 30 days)
    • merge small segments (L5), pack deltas (Git gc)
Compaction is a product decision Thinning deletes history someone may need (audit, legal hold). The retention policy must be explicit, and compaction must never remove a version still referenced by a reader, a branch or a hold.

01:07

Say

"Every immutable system eventually runs a compactor. Its cost is real (I/O, CPU, pauses) and it is where data-loss bugs hide, because it is the one component allowed to delete."

Examples

LSM storage engines (LevelDB, RocksDB) have write amplification from repeated compaction; PostgreSQL's VACUUM reclaims dead row versions — a table that is never vacuumed "bloats"; Kafka log compaction keeps only the latest value per key; Git gc packs loose objects into deltas.

Measure it

The benchmark reports "heap after trimming to the last 10 versions" and the time it takes. That is a compaction benchmark in miniature.

On disk: persistence and crashes

  • Immutable data is easy to persist: append new versions/nodes, never overwrite
  • A version is published only after its data is durable: write nodes → flush → write the new root pointer → flush
  • After a crash: the last durable root is a consistent snapshot; partial writes after it are garbage to collect
Why this is attractive No torn updates of live data, so recovery = "find the last complete root". Copy-on-write file systems and append-only B-trees (e.g. LMDB-style) rely on exactly this.

01:13

Connect to Lecture 8

"Journal first, then act" from the workflow engine and "data first, then root pointer" here are the same ordering principle: the commit point is one small atomic write, and everything it points to must already be durable.

Serialization concerns (conceptual)

In-memory pointers must become offsets or content hashes on disk; shared subtrees are written once and referenced many times. The format is part of the contract: old files must remain readable after upgrades (versioned formats).

Keep it conceptual

Do not go into fsync semantics or file-system specifics — mention only that "flush" really means "durable on stable storage", which operating systems make surprisingly hard to guarantee.

Snapshot isolation, conceptually

  • Each reader works on the version that was current when it started
  • Writers create new versions; readers never block writers or each other
  • Two writers from the same base: first commit wins; the second must detect the conflict and retry on the new version
Not a database course — one warning Snapshots give each reader a consistent view, not global correctness: two concurrent writers can each keep a rule true on their own snapshot and jointly break it ("write skew").

01:18

Example of write skew for the config platform

Rule: "at least one of the two payment regions must be enabled". Two operators, each on the same snapshot, disable a different region. Each commit is valid on its snapshot; together they disable both. Detecting this needs validation against the latest version at commit time (a compare-and-swap on the current version id) or a lock. One sentence is enough; do not go further.

API consequence

A commit API that takes an explicit parent version (commit(parent, changes)) makes this visible: if parent is not the current head, the caller knows it is committing on a stale base and can choose to rebase, merge or fail.

API design questions

Version commit(Version parent, std::vector<Change> changes);  // new id, parent unchanged
Value   get(Version v, std::size_t slot) const;              // throws if v unknown/released
bool    release(Version v);                                   // false if not allowed
bool    retire(Version v);   std::size_t compact(Version v);  // delta chain lifecycle
  • Are versions mutable after creation? (No — ever?)
  • Are ids stable across restarts and compaction?
  • Can a version be deleted while descendants exist?
  • What happens to a reader of a compacted version?
  • Is "branch" a separate operation or just commit on an older parent?
  • What exactly does "snapshot" guarantee?

01:22

Discuss two quickly

  • Delete with descendants. Options: refuse (our delta chain), cascade (dangerous), rebase descendants onto a materialised copy (costly but clean), or reference-count versions so storage goes only when no descendant needs it. Each is defensible; silence is not.
  • Branch. Our API has no separate branch(): committing on any live parent creates a branch. Simpler API, but callers may branch accidentally (stale parent). A separate branch() makes intent explicit. That trade-off (explicit vs minimal API) recurs everywhere.

Invariants of a versioned store

  1. Historical versions never change: get(v, i) is the same forever until v is released
  2. Sharing never leaks mutation: no shared node is written after it is published
  3. Ancestry stays valid: every live version can be reconstructed (its parents/deltas/checkpoints exist)
  4. References stay safe: a holder of v can finish reading, or gets a clear error — never another version's data
  5. Released/compacted data is not reachable through the API
Test #1 with an independent oracle: record every version's full state when it is created, then check them all after the whole history has been built.

01:27

Why "after the whole history"

A test that checks version v right after creating it passes even if later commits corrupt v. The mutation-leak bug only shows up when you look back. The test file does exactly this, over a branching history.

The bug (INSTRUCTOR ONLY)

PathCopyStore::commit has a "fast path": if the parent is the newest version, it mutates the tree in place via const_cast and lets the new version share the root. Consequences: (1) the parent version changes (history mutated); (2) worse, the initial tree shares one all-zero leaf among all slots, so an in-place write also changes other slots in every version, including version 0 — which is exactly what the test prints.

Why it was written

"Appending to the head is the common case and nobody reads old versions while we write" — a workload assumption turned into a correctness shortcut, as a performance optimisation without a benchmark. Review signal: const_cast on anything reachable from shared_ptr<const T>.

Fix

Delete the fast path; always path-copy (solution file). If a real in-place optimisation is wanted: only for nodes created within the same commit (a "transient"), never for published nodes.

Hints

  1. "Which store's failure message mentions version 0?"
  2. "Look for const_cast."
  3. "What else points to the leaf you just wrote?"

Where each becomes unattractive

  • Full copy: history B — 131 MB for 1,000 versions of a 128 KB array. Scale to a year of commits and it is impossible. Unbeatable reads.
  • Delta chain without checkpoints: reading anything in B costs microseconds because every read walks the chain — even the newest version (5.3 µs). Commits are almost free. Checkpoints every 32 versions cut reads ~20× (old versions) to ~190× (newest) for 4.3 MB.
  • Path copy: great for B (1.5 MB, fast reads), but in A it copies more than full copy (3.5 vs 2.8 MB) and commits are slower. 30% random changes touch every leaf; sharing buys nothing and pointers cost extra.

Workloads C and D (from the brief)

C (many old reads): full copy if memory allows, otherwise path copy; never an unbounded delta chain. D (mostly newest): anything with a cheap head. A popular real design is a mutable materialised head plus reverse deltas for history (undo logs).

What the experiment does not show

  • Allocator overhead and fragmentation (payload bytes only)
  • Disk cost: serialisation, write amplification, fsync
  • Concurrency: readers holding versions while writers commit
  • Clustered changes (real configs change related keys together)
  • Branching histories (the benchmark is linear)
  • Retention over months: compaction running continuously
  • Cost of shared_ptr atomic refcounts under threads
  • Other N, other machines
AskFor the config platform, which missing measurement would you run first, and what result would change your choice?

02:30

Expected answer

If commits are clustered and small, path copy or delta + checkpoints win; if bulk migrations dominate storage, full snapshots at migrations + deltas between them (a hybrid). Refcount cost matters only if many threads copy version handles at high rates.

Summary

  1. Versioning is a workload decision: how many versions, how big the changes, which versions are read, how long they live.
  2. Full copies, deltas and structural sharing sit on a write/read/memory trade-off curve.
  3. Structural sharing is only correct if published nodes are never mutated.
  4. Immutability moves the lifetime problem from "who writes" to "who still reads".
  5. Every immutable system needs reclamation and compaction — and a retention policy.
  6. Test history by checking every version after building the whole history.
