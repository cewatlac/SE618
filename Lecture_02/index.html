Part 1 · 00:00–00:20

Incident: the rate limiter
that stopped limiting

The incident

An API gateway keeps per-client rate-limit counters in an in-house open-addressing hash map (uint64 client_id → counter, ~60k active clients).

Platform migrates client IDs to a new scheme:

client_id = (sequence << 12) | region_code

Within an hour of the migration: gateway CPU at 100%, p99 latency from 0.4 ms to 900 ms. No code changed in the gateway. All unit tests pass.

Pairs · 3 min Propose two hypotheses. For each: what measurement would confirm it?

00:03

Let them hypothesise

Typical answers: "more clients" (no — same count), "memory leak", "lock contention", "GC". Push: "What changed? Only the distribution of the keys."

The actual mechanism (reveal on next slide)

libstdc++ and libc++ implement std::hash<uint64_t> as the identity. The in-house map computes the slot as hash & (capacity − 1) (power-of-two capacity). With a 128k-slot table, only the low 17 bits matter. Old IDs had random low bits. New IDs: the low 12 bits are the region code (a handful of values), and the sequence contributes only 5 bits above that. So ~60k keys land in a few thousand slots → giant linear-probing clusters → every lookup scans hundreds or thousands of slots.

Measurements that confirm

Profile: time in find. Instrument: average probe length (a production map should export this). Histogram of hash & mask over live keys. This is exactly the "observability" point from Lecture 1.

Real-world analogues

Many teams have hit this with pointer keys (allocations are 16-byte aligned, so low 4 bits are always zero), with IDs that are multiples of page sizes, and with timestamps in milliseconds rounded to seconds.

What actually happened

  • std::hash<uint64_t> is the identity in libstdc++ and libc++
  • Slot = hash & (capacity − 1) keeps only the low bits
  • New IDs share their low 12 bits → keys pile into a few slots
  • Linear probing turns piles into long clusters

Numbers

Why is std::unordered_map fine (even faster) on the strided keys?

libstdc++ uses a prime bucket count and hash % bucket_count. Modulo a prime uses all bits of the hash, so structured keys spread. Its identity hash + prime modulus is a deliberate pairing. It is even faster than random here because consecutive strided keys hit sequential buckets, which is cache-friendly. Power-of-two tables (Abseil, Folly F14, Rust's hashbrown, our FlatMap) are faster at computing the index (mask vs division — division is ~20–40 cycles) but require a hash with good low bits, so they mix the hash first.

The engineering lesson

The hash function and the index-reduction are a matched pair. Swapping one without the other is a latent bug that waits for a key distribution change.

Precise statement

The classical result: with simple uniform hashing (or universal hashing with a randomly chosen function), the expected cost of an operation is O(1 + α) for chaining, where α = n/m is the load factor. "Expected" is over the random choice of hash function (universal hashing) or over a random input distribution (simple uniform hashing assumption). A fixed, public hash function gives no guarantee against a chosen input — that is the adversarial row.

Part 2 · 00:20–01:00

Contracts: hashing, equality
and the adversary

The hashing contract

Required (correctness)

  1. eq(a, b) ⇒ hash(a) == hash(b)
  2. eq is an equivalence relation
  3. Hash and equality of a key must not change while it is in the map
  4. Deterministic within the process

Desired (performance)

  • Unequal keys rarely collide in the bits the table uses
  • Cheap to compute relative to the lookup
  • Resistant to chosen inputs, if keys are untrusted
Violating a "required" rule gives wrong answers. Violating a "desired" rule gives slow answers — much harder to notice.

00:20

Rule 3 in practice

A key is a struct; someone mutates a field through a pointer after insertion. The entry is now in the wrong bucket: find with the new value misses it, find with the old value finds the bucket but equality fails. The map is corrupted with no crash. C++ makes the key const in value_type precisely to prevent this; but keys holding pointers to mutable data escape that protection.

Rule 4

Not necessarily across processes: many languages randomise hash seeds per process (Python since 3.3 for str, Rust's default SipHash with random keys). Consequence: never persist hash values or rely on iteration order across runs.

Ask

"Is hash(x) = 0 for all x a correct hash function?" Yes — correct, and every operation O(n). A great test tool: it forces every collision path (use it in Part 5's test strategy).

Spot the bug

struct Email { std::string addr; };

struct EmailEq {                       // "emails are case-insensitive"
    bool operator()(const Email& a, const Email& b) const {
        return iequals(a.addr, b.addr);
    }
};
struct EmailHash {
    std::size_t operator()(const Email& e) const {
        return std::hash<std::string>{}(e.addr);
    }
};

std::unordered_map<Email, UserId, EmailHash, EmailEq> users;
users[{"Ali@Example.com"}] = 42;
auto it = users.find({"ali@example.com"});   // ?

00:27 Give 60 seconds.

Answer

Equality is case-insensitive; hash is case-sensitive. The two strings are equal under EmailEq but hash differently → rule 1 violated → find usually misses (it looks in a different bucket), but occasionally finds it when the two hashes happen to land in the same bucket. Non-deterministic-looking bug, depends on table size. Worse: users[...] can create a second entry for the same logical user → duplicate accounts.

Fix options

  • Hash the case-folded string (and fold the same way in equality).
  • Better design: normalise at the boundary — store a canonical lower-cased Email type, so plain equality and plain hash are correct by construction. Normalisation is a recurring theme; it returns in Lecture 4 (Unicode).

Deeper point

Is email local-part really case-insensitive? RFC 5321 says the local part may be case-sensitive; most providers treat it as insensitive. This is a product decision encoded in an equality function. Good engineering writes it down.

Hash quality: which bits does the table use?

Mixing ("finalising") fixes weak hashes cheaply:

uint64_t mix64(uint64_t x) {   // splitmix64
    x ^= x >> 30;
    x *= 0xbf58476d1ce4e5b9ULL;
    x ^= x >> 27;
    x *= 0x94d049bb133111ebULL;
    return x ^ (x >> 31);
}
Avalanche: flipping one input bit should flip each output bit with probability ≈ ½. Identity hashing has zero avalanche.

00:32

Explain the three reductions

  • Modulo prime: libstdc++'s choice. Robust to weak hashes; division is slow; resizing must jump to the next prime in a table.
  • Mask: fastest; demands good low bits. Abseil/hashbrown/F14 all mix the user's hash first.
  • Fibonacci / multiplicative hashing (Knuth): multiply by ≈2⁶⁴/φ and take the top k bits. Cheap and uses all bits.

Cost of mixing

Two multiplies and three shifts: ~3–5 ns worst case, usually hidden by memory latency. Our benchmark: FlatMap random-key lookup 6 → 8 ns with mixing, strided 838 → 8 ns. Pay 2 ns everywhere to remove a 100× cliff: that is the kind of trade you should be able to argue.

For strings

Production string hashes: wyhash, xxHash3, SipHash (keyed, DoS-resistant, slower), CityHash/FarmHash. Hashing a 36-byte key costs more than the table probe for small tables.

Adversarial inputs: hash flooding

If an attacker can choose keys and knows the hash function, they can send n keys that all collide → each insert O(n) → Θ(n²) total.

2011: one ~2 MB HTTP POST with crafted form-field names kept a CPU core busy for minutes in PHP, Java, Python, Ruby, ASP.NET servers.

Defences

  • Keyed hash with a secret per-process seed (SipHash)
  • Limit untrusted input size (field counts, JSON keys)
  • Bucket overflow into a balanced tree (Java 8 HashMap)
AskOur rate-limiter keys are client IDs we assign. Do we need SipHash? What about a map keyed by User-Agent strings?

00:38

Background

Klink & Wälde, "Efficient Denial of Service Attacks on Web Application Platforms", 28C3 (Dec 2011). The fix across languages was randomised/keyed hashing. Python adopted SipHash for str (PEP 456); Rust's HashMap uses SipHash-1-3 with random keys by default; Java 8 converts long bucket chains to red-black trees (worst case O(log n) per bucket).

Expected answer

  • Client IDs we assign: not attacker-chosen → a fast non-keyed hash + mixing is fine. But beware: who chooses IDs can change later (the incident!).
  • User-Agent: attacker-controlled strings → keyed hash, or cap the map size, or don't key on it.

Engineering point

The threat model is a requirement. "Where do keys come from?" belongs in the design document, next to the hash function choice.

C++ note

std::hash is not keyed and gives no DoS resistance. Use a keyed hash for untrusted keys.

Part 3 · 01:00–01:30

Collisions, load, resizing,
deletion and layout

Two families of collision handling

Separate chaining

Each node a separate allocation. Load α may exceed 1. Stable addresses.

Open addressing (linear probing)

No per-entry allocation, cache-friendly. α must stay < 1. Moves on rehash.

01:00

Say

"Everyone knows both from undergrad. The question for us is: what does each cost in memory, in cache misses, and in contract?"

Comparison to draw out

  • Chaining: lookup = bucket array load + one or more node loads (each a likely cache miss for large tables). Memory per entry: node (next 8 + key + value + optionally cached hash 8) + allocator header (~16) + bucket pointer 8. Degrades gracefully as α grows.
  • Linear probing: lookup = usually one cache line holds several slots, so probing a few more slots is nearly free. Memory: slot size × capacity; at α = 0.5 you pay for 2× slots. Degrades sharply near α → 1 (next slide).
  • Other open-addressing schemes: quadratic probing, double hashing, Robin Hood (reduces variance of probe lengths), cuckoo hashing (worst-case O(1) lookup, complex insertion), Swiss tables (groups of 16 slots with 1-byte metadata scanned by SIMD).

Load factor: where the cliff is

Expected probes, linear probing (Knuth):

hit ≈ ½ (1 + 1/(1−α))
miss ≈ ½ (1 + 1/(1−α)²)

Chaining: hit ≈ 1 + α/2, miss ≈ α

Misses degrade quadratically in 1/(1−α). Workloads dominated by misses (dedup of new IDs, negative caches) feel the cliff first.

01:06

Connect to workload

Lecture 1's dedup component: 99% of lookups are misses (new IDs). A max load of 0.9 would look fine in a benchmark of hits and be terrible in production. The operation mix determines which column matters.

Memory vs speed trade

α = 0.5 → 2× memory of α = 1 in slot storage. Many production maps run 0.5–0.875 (Swiss tables allow 7/8 because SIMD scanning makes long probes cheap). Picking α is picking a point on a memory/latency curve — it should be justified by the workload.

Caveat

Formulas assume uniform hashing. With a weak hash the effective α within a cluster is ~1 regardless of the global α — the incident.

Resizing: amortised cheap, individually expensive

  • Doubling gives amortised O(1) insert — total work ≤ 2n moves
  • But the insert that triggers it pays O(n): at 16M entries that is hundreds of milliseconds
  • Rehash also doubles memory temporarily (old + new arrays)
  • Open addressing: rehash moves every element → all pointers invalidated

Mitigations

  • reserve(n) when n is known
  • Incremental rehash: migrate a few buckets per operation (Redis dict)
  • Shard into many small tables (bounded pause per shard)
  • Never shrink automatically, or shrink with hysteresis
AskWhy is "grow at 0.75, shrink at 0.25" better than "grow at 0.75, shrink at 0.70"?

01:12

Answer

Thrashing. With close thresholds, a workload oscillating around the boundary (insert one, erase one) triggers a full O(n) rehash on every operation. A wide gap (hysteresis) guarantees Θ(n) cheap operations between resizes, preserving the amortised bound.

Redis detail (if asked)

Redis dictionaries keep two tables during rehash; each lookup/insert migrates one bucket (plus a time-bounded background step); lookups check both tables. Latency stays bounded at the cost of complexity and 2× memory during migration.

Memory spike

The temporary 2× is often what gets containers OOM-killed: a pod at 60% memory grows its main table and dies. The memory budget must include the rehash peak.

Deletion in open addressing

Just mark slot empty?

Breaks probe chains: keys inserted after a collision become unreachable. wrong answers

Tombstones

Mark "deleted": lookups skip it, inserts may reuse it. Accumulate under churn → must count toward load and be purged. subtle

Backward-shift deletion (linear probing only)

After removing a slot, shift later entries of the cluster back into the gap. No tombstones, but erase costs a cluster scan and moves elements (invalidating pointers).

01:17

Say

"Deletion is where most hand-written open-addressing maps are broken. The lab after the break contains a map that uses tombstones — and still has two deletion-related bugs. Keep this slide in mind."

Tombstone subtleties (don't give away the lab — just state principles)

  • A lookup stops only at an empty slot, never at a tombstone.
  • Inserting into a tombstone is safe only when you know the key is not further along the chain.
  • Load factor must include tombstones, otherwise the table can run out of empty slots.

Workload link

Churn-heavy workloads (sessions, caches, dedup windows — Lecture 1's RecentWindow!) generate a delete for every insert. Tombstone policy is a first-order design decision for them.

01:22

Classic bugs

  • Holding auto& v = m[k1]; then m[k2] = ...; then using v: fine with std::unordered_map, dangling with a flat map. Migrating a codebase from one to the other silently introduces use-after-free. ASan catches it.
  • Tests that compare printed map contents in order: pass today, fail after a library upgrade changes the hash seed or growth policy.
  • O(capacity) iteration: a map that once held 10M entries and now holds 10 still iterates 16M slots if it never shrinks — "clear() is fast, iteration is slow" surprises.

Design advice for projects

If deterministic output is a requirement (reports, reproducible tests), sort on output or use an ordered structure; do not rely on hash order.

01:26

Explain the rows

  • Node: next 8 + key 8 + value 8 (+ cached hash 8 for some key types) = 24–32 B, malloc rounds up and adds ~8–16 B header → 32–48 B; plus 8 B bucket pointer at α≈1.
  • Our lab slot: 1-byte state padded to 8 + key 8 + value 8 = 24 B; at α 0.5–0.75 → 32–48 B per live entry. Storing the state bytes separately (as Swiss tables do) removes padding.
  • Sorted vector: no overhead at all, but O(n) insert. For read-mostly data (built once, queried often) it is often the fastest and smallest — a recurring alternative in Lectures 4 and 6.

The three defects (INSTRUCTOR ONLY)

  1. D1 — duplicate keys via tombstone reuse (correctness). insert_or_assign writes into the first Tomb it meets, without checking whether the key already exists further along the probe chain. Sequence: keys a, b collide (b placed after a); erase a (tombstone); insert b again → goes into a's tombstone → two live copies of b, size() too large; erase b removes one copy, contains(b) still true.
  2. D2 — tombstones ignored in load factor (performance, eventually liveness). Growth checks size_ only. Under churn (erase + insert of fresh keys), tombstones accumulate until there are no Empty slots left; every miss then scans the whole table (bounded only by the loop counter). Benchmark: lookup_miss_after_churn ~22,000 ns vs ~20 ns.
  3. D3 — identity hash + mask (performance). std::hash<uint64_t> is identity; & mask uses only low bits; strided keys cluster. Benchmark: lookup_strided_keys ~840 ns vs ~8 ns.

Hints to give progressively (only if stuck)

  1. "Print the map's size and the reference size at the mismatch. Which is larger?"
  2. "Which operations ran just before on keys that share a slot?"
  3. "For the benchmark: which workloads are slow? What is special about their keys / history?"
  4. "How many Empty slots are left after churn? Add a counter."

The insert path — read it with tombstones in mind

bool insert_or_assign(const K& k, const V& v) {
    if ((size_ + 1) * 4 > slots_.size() * 3) grow();       // max load 0.75
    std::size_t i = index(k);                               // Hash{}(k) & mask()
    for (;;) {
        Slot& s = slots_[i];
        if (s.st == State::Empty || s.st == State::Tomb) {
            s.st = State::Full; s.key = k; s.val = v; ++size_;
            return true;
        }
        if (s.key == k) { s.val = v; return false; }
        i = (i + 1) & mask();
    }
}

A benchmark plan for a hash map

Independent variables

  • n: in L1, L2, L3, and ≫ LLC (e.g. 10³ … 10⁸)
  • Load factor at measurement time
  • Key type/size: int, 16 B ID, 40 B string
  • Distribution: random, sequential, strided, skewed
  • Mix: hit/miss ratio, insert/erase churn

Metrics

  • ns/op median + spread; p99 and max for inserts (rehash)
  • Bytes per entry (allocator stats or RSS delta)
  • Probe length / chain length histogram

Baselines

  • std::unordered_map with reserve, and without
  • Sorted vector if data is read-mostly

02:27

Details worth teaching

  • Sizes across cache levels: performance steps when the working set leaves L2 (~1–2 MB) and LLC (~10–50 MB). A benchmark only at 65k keys measures cache-resident behavior.
  • Random lookup order: iterating keys in insertion order can accidentally be cache-friendly (sequential keys with identity hash!). Shuffle the lookup sequence.
  • Measuring rehash pauses: time each insert individually (or in batches of 64) and report the max and p99.9 — the mean hides them completely.
  • Memory: custom allocator counting bytes, or mallinfo2/GetProcessMemoryInfo deltas; divide by n.
  • Fair baseline: give std::unordered_map the same reserve and the same (mixed) hash where relevant; otherwise you measure the hash, not the table.

With everything in one cluster, every probe path, wrap-around at the end of the array, and tombstone interaction is exercised with a tiny test. This is "design for testability" from Lecture 1 applied again.

Performance as a test

Wall-clock tests are flaky. Instead assert on a deterministic proxy: average probe length for 10k strided keys < 3. It fails deterministically when hash quality regresses.

The ASan test

This is a test that should crash under ASan for a flat map, documenting that pointers are invalidated. Keep it disabled by default or as a "death test" — its value is making the contract explicit.

API choices with consequences

V& operator[](const K&)A lookup of a missing key inserts it. Reads can grow the map, cannot be const.

std::optional<V> get(const K&)Safe, but copies V on every lookup

02:45

operator[] story

A metrics service did if (counters[name] > limit) for every incoming request name, including garbage names from scanners. Each read inserted a zero entry. Memory grew without bound until OOM. Classic. The fix is find; the lesson is that an API whose read path mutates is a footgun.

Heterogeneous lookup

C++20: unordered_map supports it with is_transparent hash and equality. The contract: hash(string_view(s)) == hash(s) for all s. That is rule 1 across types.

Project connection

Almost every project contains a hash map somewhere. In your design document (due 31 Oct) you should be able to state:

  • Where keys come from — trusted or attacker-influenced?
  • Key distribution — and what happens if it changes
  • Operation mix — hit/miss ratio, churn
  • Load factor, growth policy, peak memory incl. rehash
  • Pointer/iterator lifetime your API exposes
  • Why the standard map is — or is not — good enough
Default advice Start with std::unordered_map + reserve. Replace it only when a measurement on your workload shows it is the bottleneck — and keep it as your baseline.

Summary

  1. Hash + index reduction are a matched pair; identity hash + mask fails on structured keys.
  2. Rule 1: equal keys must hash equal. Normalise at the boundary.
  3. Untrusted keys need a keyed hash or bounded input — the threat model is a requirement.
  4. Load factor must count tombstones; misses feel the cliff first.
  5. Amortised O(1) hides O(n) rehash pauses and 2× memory peaks.
  6. Contracts (stability, iteration) constrain layout; flat maps are faster because they promise less.
  7. Benchmarks that ignore distribution and churn can crown a broken map.
