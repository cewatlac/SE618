Part 1 · 00:00–00:20

Scenario: the product page
is too slow

The scenario

An e-commerce product-detail service renders pages from a pricing + inventory database.

  • 5,000 requests/s at peak; 2 million products
  • DB query: 40 ms median; the DB saturates above 1,500 queries/s
  • SLO: page data in ≤ 15 ms at p50
  • Each service instance may use 1 GB for caching; product record ≈ 2 KB
  • Prices change a few times a day; stock changes every few seconds for popular items
Before any policy discussion What hit rate do we need — and for which requirement: latency or database load?

00:03 Let students compute for 3 minutes; then next slide.

Why this scenario

It has two competing constraints (latency SLO and backend capacity), a memory budget that cannot hold everything (2M × 2 KB = 4 GB > 1 GB), and data with different staleness tolerance (price vs stock). All the day's themes appear.

The arithmetic of caching

Latency (hit ≈ 0.2 ms, miss ≈ 40 ms):

E[t] = h · 0.2 + (1 − h) · 40 ≤ 15 → h ≥ 0.63

Database load:

(1 − h) · 5000 ≤ 1500 → h ≥ 0.70

Capacity: 1 GB / (2 KB + ~100 B overhead) ≈ 480k products = 24% of the catalogue

Consequences
  • The binding constraint is DB load, not latency.
  • We need 70%+ of requests served from 24% of the items → only works if popularity is skewed.
  • A mean of 15 ms still means 30% of users wait 40 ms. Is p50 the right SLO?

00:07

Walk through

  • Latency: 0.2h + 40 − 40h ≤ 15 → 39.8h ≥ 25 → h ≥ 0.628.
  • DB: misses per second must stay under 1500 → h ≥ 0.7. Note: a cache cold start (deploy, restart) sends 5000 q/s to the DB — it falls over. Cache warm-up is a requirement (Part 3: stampedes).
  • Per-entry overhead: map node + list node + key + metadata ≈ 64–128 B; small relative to a 2 KB value but dominant for small values (e.g. caching booleans).

Point about percentiles

With h = 0.7, the p50 is a hit (0.2 ms) but the p75 and above are misses (40 ms). Caches make latency bimodal; the mean describes nobody. The SLO should be stated as a percentile, and the cache can only fix percentiles below the hit rate.

Transition

"So the whole design rests on one question: is popularity skewed, and does it stay skewed? That is locality."

Why caches work at all: locality and skew

Temporal locality

Recently used items are likely to be used again soon. LRU bets on this.

Frequency skew

A few items get most requests (Zipf-like). LFU bets on this.

Spatial locality

Neighbours of used items get used. CPU caches, prefetching, pages.

Zipf's law, informally Request probability of the item with popularity rank r ∝ 1 / rs. With s ≈ 0.9 over 100k items, the top 1% of items receive roughly 47% of requests; the top 5%, about 63%.
If there is no skew and no recency (uniform random access), no policy helps: hit rate ≈ capacity / catalogue.

00:12

Say

"Every eviction policy is a bet about the future, made from the past. LRU bets that the recent past predicts the near future. LFU bets that long-run popularity does. Both bets are sometimes wrong, and we can construct the workloads where they are."

Evidence on skew

Web object popularity, video views, and key-value store traces are often reported as Zipf-like with s between 0.6 and 1.0 (e.g. Breslau et al., INFOCOM 1999, for web caches). But real traces also have churn: popularity shifts over hours (news, sales).

Check

The figure: for s = 0.9, N = 100k, the share of the top 1000 ranks is H(1000, 0.9)/H(100000, 0.9) ≈ 0.47 (top 5000: ≈ 0.63). That is the ceiling for a cache of that size holding exactly the most popular items (an oracle). Our simulation shows 0.34–0.45 at capacity 1000 and 0.48–0.60 at 5000 — the gap to the oracle is the price of predicting popularity from the past.

Say

"Hit rate is the metric everybody reports and nobody's actual goal. The goal is latency, backend protection, or cost — with a bound on staleness. Choose the metric from the requirement."

Example

A CDN optimising byte hit rate keeps large video segments; one optimising request hit rate keeps many small thumbnails. Same infrastructure, opposite policies. Cost-aware policies (GreedyDual-Size) weigh by cost/size.

Observability requirement

A production cache must export at least: hits, misses, evictions, size (entries and bytes), load/fill latency, and (ideally) age of served entries. The lab's CacheStats is the minimal version.

Part 2 · 00:20–01:00

LRU and LFU: designs,
invariants and costs

LRU: requirement → structure

OperationNeedsStructure
get(k)Find k in O(1)hash map
on hitMove k to "most recent" in O(1)doubly linked list + node handle
on full putFind and remove the least recent in O(1)list tail

Map value = iterator into the list. std::list::splice moves a node without invalidating any iterator.

Invariants
  1. index.size() == items.size() ≤ capacity
  2. For each node n: index[n.key] == n
  3. Each key appears in exactly one node
  4. List order = recency order (front = most recent)
  5. hits + misses = number of get calls

00:20

Say

"You all know this structure. It is the same shape as Lecture 1's RecentSet — map + list — but with recency refresh on read, which RecentSet deliberately did not do. Same data structure, different contract, different product."

Why a list, not a vector or deque?

We need O(1) removal from the middle and stable handles. std::list::splice relinks a node in O(1) and all iterators remain valid — the invariant #2 depends on it. A vector would invalidate stored indices on every move.

Cost awareness

Per entry: list node (2 pointers + key + value) + map node (key copy + iterator + next + hash) → key stored twice, ~64+ B overhead, 2 allocations per insert. For small values, overhead exceeds payload. Production caches use intrusive lists, a single node allocation holding both, or approximations (CLOCK) that avoid the list entirely.

LRU: the core in C++

std::optional<V> get(const K& k) {
    auto it = index_.find(k);
    if (it == index_.end()) { ++stats_.misses; return std::nullopt; }
    ++stats_.hits;
    items_.splice(items_.begin(), items_, it->second);   // move to front, O(1)
    return it->second->second;                           // copy out: no dangling ref
}

void put(const K& k, V v) {
    if (auto it = index_.find(k); it != index_.end()) {   // existing: update + refresh
        it->second->second = std::move(v);
        items_.splice(items_.begin(), items_, it->second);
        return;
    }
    if (items_.size() == cap_) {                          // new key, full: evict LRU
        index_.erase(items_.back().first);
        items_.pop_back();
        ++stats_.evictions;
    }
    items_.emplace_front(k, std::move(v));
    index_[k] = items_.begin();
}

00:27

Teaching sequence

Do not dwell — they can write this. Point to three engineering decisions:

  1. get returns a copy in an optional, not a reference: a reference would dangle when another put evicts the entry (Lecture 1's lifetime point). For 2 KB values, copy cost is real; alternatives: shared_ptr<const V> (shared ownership, readers keep evicted values alive safely).
  2. get mutates the structure. Therefore it cannot be const, and in a concurrent setting a read needs a write lock. This is the key concurrency fact of LRU (Part 3).
  3. The update path in put is where hand-written LRUs usually break. The lab has exactly such a bug.

Don't show during the lab

This slide is effectively the fix for the lab. If you prefer, skip it now and show it in the debrief.

LFU in O(1): frequency buckets

  • entry: key → (freq, iterator)
  • by_freq: freq → list of keys (LRU order within a frequency)
  • min_freq: bucket to evict from

On hit: move key from list f to list f+1; if list f emptied and f == min_freq, min_freq++.

On insert: freq = 1, min_freq = 1.

00:35

Explain

Reference: Shah, Mitra, Matani, "An O(1) algorithm for implementing the LFU cache eviction scheme" (2010). Our LfuPolicy in cache_policies.hpp implements it with an unordered_map<freq, list>.

Why min_freq only ever needs +1 on hit

A hit moves one key from f to f+1. If bucket f becomes empty and it was the minimum, the new minimum is f+1 (the key we just moved is there). An insert resets min_freq to 1. So no search is needed — O(1).

Point at the bottom-right label

k1 and k5 have frequency 17 because they were popular last week. They will never be evicted while new items keep entering at freq 1 and being evicted first. This is cache pollution by stale popularity — LFU's classic failure, and the reason for aging/decay (halve all counters periodically) or windowed frequency (W-TinyLFU in Caffeine).

Second failure: new-item starvation

A newly popular item enters at freq 1 and competes with every one-hit wonder; it can be evicted before it accumulates enough hits. SLRU and W-TinyLFU address this with a small "window" or probation segment.

More policies: each is a different bet

PolicyBetDefeated byCost

00:43

Notes per row

  • LRU and loops: cyclic access over C+1 items with capacity C: every access misses, because the item needed next is always the one just evicted. Common in practice: iterating a table slightly larger than the buffer pool (databases call this "sequential flooding").
  • SLRU: new items enter probation; a second hit promotes them to protected. One-time scans cycle through probation only. Used in many buffer managers; 2Q (Johnson & Shasha, VLDB 1994) is a close relative.
  • Random: seems naive but is robust — no pathological pattern, no per-hit bookkeeping (important under concurrency). Redis's "LRU" is actually sampled: evict the least recent of ~5 random keys.
  • CLOCK: a circular buffer with a reference bit; hits set the bit, the hand clears bits until it finds a 0. Approximates LRU without moving nodes — used by operating systems for page replacement.
  • Modern: ARC (adaptive between recency and frequency), LIRS, W-TinyLFU (Caffeine), S3-FIFO (2023, simple FIFO queues with strong results on real traces). Mention; do not teach in detail.

stampedes, capacity, concurrency

TTL and stale data: a separate decision from eviction

Eviction answers: what to drop when full?
Expiry answers: when is a value no longer true enough?

DataTolerable stalenessMechanism

Ask Expire-after-write or expire-after-access for prices? What goes wrong with the other one?

01:00

Answer

Expire-after-write (TTL measured from when the value was loaded). Expire-after-access keeps refreshing the deadline on every read: a popular product's price would never expire and could be stale forever. Expire-after-access is appropriate for sessions (idle timeout), not for data freshness.

Implementation notes

  • Lazy expiry: check the timestamp on read, treat expired as a miss. Cheap, but expired entries still occupy memory until evicted.
  • Active expiry: a timer wheel or a min-heap by deadline, or sampling (Redis samples 20 keys with TTL ten times per second).
  • Same "inject the clock" design point as Lecture 1's RecentWindow.

Product point

Checkout must re-read price/stock from the source of truth. The cache serves the browse path. Different consistency requirements per path is normal — and must be written down.

Cache stampede (thundering herd)

A popular key expires (or the cache restarts). In the next 40 ms, every request for it misses and queries the database.

At 5,000 req/s on one hot product: ~200 identical DB queries before the first one returns. Across many keys after a restart: the DB falls over; it cannot recover because the cache cannot fill.

Mitigations

  • Request coalescing (single-flight): one loader per key; others wait
  • Jittered TTLs: avoid synchronized expiry
  • Early probabilistic refresh before expiry
  • Serve stale while revalidating
  • Warm-up before taking traffic
A cache that improves the average can make the system less stable: the backend is now sized for the hit rate, not for the traffic.

01:07

Say

"This is the most important operational idea today. Once you add a cache, your database is provisioned for 30% of traffic. The cache has become a load-bearing component. Its failure modes are now system failure modes."

Details

  • Single-flight needs a per-key "loading" state: a map from key to a shared future. Data-structure consequence: entries have states (absent / loading / present / stale), not just present/absent. Invariant: at most one load in flight per key.
  • Probabilistic early expiration ("XFetch", Vattani et al., VLDB 2015): each reader refreshes early with probability increasing as expiry nears; the expected number of concurrent refreshes stays ~1.
  • Stale-while-revalidate: HTTP Cache-Control extension (RFC 5861). Trades staleness for availability — acceptable for descriptions, not for checkout prices.
  • Real incident pattern: cache cluster restart → DB overload → timeouts → retries (Lecture 1!) amplify load → outage.

Capacity is bytes, not entries

  • Values vary: 200 B … 200 KB. "capacity = 10,000 entries" bounds nothing.
  • Overhead per entry (nodes, key copies, pointers, allocator) is often 64–150 B.
  • Budget must include: fragmentation, rehash peak (Lecture 2), in-flight loads.

Weighted capacity: evict until Σ weight(entry) ≤ budget. One insert may evict many entries — or be rejected.

Ask A single 900 MB value arrives for a 1 GB cache. What should put do? Where is that decided — in code or in the contract?

01:13

Expected answer

Admitting it would evict almost everything (catastrophic hit-rate drop) for one value that may be used once. Reasonable contracts: reject values above a max size (e.g. 1% of budget) and report it via a counter; or route large objects to a separate cache. It must be in the contract, because callers will otherwise assume put implies a later get hit.

Admission vs eviction

This is an admission policy: deciding whether to insert at all. TinyLFU's key idea is admission: admit a new item only if its estimated frequency (from a compact sketch — Lecture 10) exceeds the eviction victim's. Admission control is often more effective than a smarter eviction policy.

Invariant change

With weights, the invariant becomes Σ weight ≤ budget, and eviction becomes a loop — the O(1) claim becomes amortised O(1) per unit of weight inserted.

Thread-safety, conceptually

  • LRU's get writes (moves a node). A read-write lock does not help: every request needs the write lock.
  • One mutex around the cache → all cores serialise on it. Throughput stops scaling at a few cores.
  • Options:
    • Sharding: N independent caches by hash(key)
    • Approximate recency: CLOCK bits, sampled LRU
    • Buffered updates: record hits in a lossy buffer, apply in batches
Trade Every scalable option gives up exact LRU order. Sharding also gives up a global capacity bound per key-space region. Decide what "LRU" means in your contract.

01:20

Depth for today: conceptual only

Week 11 covers concurrency in detail. Today: recognise that sequential correctness ≠ concurrent scalability, and that "exact LRU" is an expensive promise.

Examples

  • Caffeine (Java) records reads into striped ring buffers and replays them under a lock asynchronously; reads never block on the policy.
  • memcached uses segmented LRU with a background maintainer thread; items bumped at most once per 60 s to limit lock traffic.
  • Sharding: 16 shards each with capacity C/16; skewed keys can make one shard hot and another idle — per-shard hit rates differ.

Other concurrency hazard

Returning references into the cache (instead of copies or shared_ptr) is a use-after-free under concurrency: another thread evicts the entry while the reader uses it.

01:40

Defects (INSTRUCTOR ONLY)

  1. B1 — get does not refresh recency. The cache is FIFO for reads. Caught by the "recency" test. In production: hit rate silently drops (our sim: LRU 0.515 vs FIFO 0.475 on Zipf at C = 5000) — no error, just a worse number that nobody attributes to a bug.
  2. B2 — put of an existing key creates a second node. Also, when full, it evicts even though no new key is being added. The map points at the new node; the stale node remains in the list. Later the stale node reaches the tail and its eviction erases the map entry of the live key → the key vanishes although its node is still in the list; index.size() != items.size(); evictions over-counted; memory leaks slowly as orphaned nodes accumulate. Caught by the differential test via size mismatch (seed 3, step 6).

Answer to Q4

B1: nothing crashes, nothing is wrong per request; only an aggregate metric is slightly worse. The only defence is a recency test written from the contract. B2 at least eventually shows up as missing keys/memory growth.

02:05 Let the table sit for 20 seconds before speaking.

Explain each row

  • zipf: stable popularity → frequency is the best predictor → LFU ≈ SLRU > LRU > FIFO ≈ Random.
  • zipf + scans: every scan flushes LRU and FIFO completely (10,000 one-off keys > capacity), losing 8 points. LFU and SLRU protect items seen more than once. (LFU is barely affected: scan keys have freq 1 and are evicted first.)

  • loop: the pathological case. For LRU and FIFO the next needed key is always the one just evicted. LFU/SLRU also fail (every key has freq 1 when evicted). Random keeps a random ~C of the loop and hits often.

Part 5 · 02:20–02:45

Interpreting the experiment

What the simulation shows — and what it does not

Supported

  • Policy ranking depends on workload structure
  • LFU is fragile under popularity shift
  • LRU is fragile under scans and loops
  • A small segmented design is robust across 3 of 4

Not supported

  • That real traffic looks like these generators
  • Latency or throughput (only hit rate)
  • Memory overhead of each policy's metadata
  • Behaviour under concurrency, TTLs, variable sizes
  • Variance: one seed, no confidence intervals
AskYou must pick one policy for the product-page service. What additional evidence would you collect first?

02:20

Expected answer

  1. A real trace: log (timestamp, product ID, response size) for a day, including the nightly batch jobs and a sale event. Replay it through the simulator — trace-driven simulation is the industry standard for policy selection.
  2. Miss-ratio curve: hit rate vs capacity for each policy (simulate many capacities). It answers "is it worth buying more memory?" — sometimes a bigger LRU beats a smarter policy.
  3. Shadow deployment: run a second policy in production on a sample of traffic, tracking hits without serving from it.
  4. Per-op cost: LFU does more work per hit (two list operations and a hash lookup on freq); measure ns/op and memory per entry.

Also

Results at capacity 1,000 and 5,000 agree in ranking; that is weak evidence of robustness across sizes. More capacities → miss-ratio curve.

Stats identities

Counters are part of the contract (dashboards and alerts depend on them). The identity evictions == new_inserts − size (for a cache that only removes by eviction) catches B2's over-counting.

Deterministic hit-rate regression

Replaying a fixed trace through the policy gives an exact hit count — deterministic, unlike timing. Assert it equals the recorded value; any change to policy code that changes the number must be deliberate. Same idea as Lecture 2's "probe length" proxy.

Summary

  1. Work out the required hit rate from latency and backend load before choosing a policy.
  2. Every policy is a bet about the future; each has a workload that defeats it.
  3. LRU = map + list with O(1) splice; its get is a write — which matters for concurrency.
  4. LFU needs aging; SLRU/2Q resist scans; Random survives loops.
  5. Expiry ≠ eviction. Choose staleness per data type and per path.
  6. Caches become load-bearing: plan for stampedes, cold starts and byte budgets.
  7. Evaluate with traces and predictions, not with a single synthetic benchmark.
