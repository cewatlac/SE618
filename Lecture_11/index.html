Part 2 · 00:15–00:55

Concurrent correctness

Sequential invariants are not enough

Sequential invariant

"After every public call, size() equals the number of entries."

Concurrent requirement

  • Invariants hold at every point another thread can observe
  • Each operation appears to happen at one instant (linearizability)
  • Compound operations must be atomic as a whole if callers rely on them
// every call is thread-safe ...
uint64_t v = map.get(k);   // locked
map.put(k, v + 1);         // locked
// ... the sequence is not:
// T1 get=5   T2 get=5
// T1 put 6   T2 put 6   → one update lost

00:15

Say

"'Thread-safe' is a property of single calls. Your callers think in terms of operations — 'increment the counter', 'transfer money'. If the API only offers get and put, every caller will write this race. The fix is an API that offers the compound operation atomically: increment(k), compute(k, f), compare-and-set."

Linearizability, one sentence

Each operation behaves as if it happened at a single point between its call and its return, and all threads agree on that order. A mutex around each operation gives it trivially; lock-free designs have to argue for it.

This is measured later

concurrency_test.cpp shows exactly this lost update — and that ThreadSanitizer cannot see it.

Races, atomicity, visibility

ProblemWhat goes wrongTool
Data raceTwo threads access the same memory, at least one writes, no synchronisation → undefined behaviour in C++mutex, atomics; ThreadSanitizer finds them
Atomicity violationEach step is synchronised, but the sequence is notAPI design, a larger critical section
Visibility / orderingA write is not seen by another core, or seen in a different orderRelease/acquire via mutex or atomics
Memory ordering, conceptuallyCompilers and CPUs reorder memory operations. A mutex unlock (release) followed by a lock (acquire) guarantees that everything written before the unlock is visible after the lock. Relaxed atomics give atomicity without ordering.

00:22

Keep this conceptual

Do not teach the C++ memory model. The three facts students need: (1) a data race on non-atomic data is UB — the program can do anything, including "work in testing"; (2) mutexes provide both mutual exclusion and visibility; (3) std::atomic with the default seq_cst is the safe default; weaker orderings are an expert optimisation that needs a proof.

Classic visibility bug

A publisher sets data = ...; ready = true; with plain variables; the consumer spins on ready and reads stale data (or loops forever because the compiler hoisted the read). Fix: make ready an atomic with release/acquire.

Our false-sharing experiment

It uses fetch_add(1, memory_order_relaxed): each counter only needs atomicity, not ordering with other data. That choice is justified in one sentence — and every weaker ordering in your code should be.

00:28

Sharding details

  • Choose the shard by a mixed hash (Lecture 2): if keys share low bits and you take k % 64, all keys can land in one shard.
  • Align each shard to its own cache line(s) — otherwise neighbouring locks falsely share (our alignas(64)).
  • Global operations (total size, iteration) either lock all shards in a fixed order (deadlock-free, slow) or return a non-atomic, approximate answer — document which (our total() says it is not a snapshot).

Reader-writer locks

Intuition says "90% reads → RW lock". Reality: even readers write to the lock's shared counter, so the cache line still bounces; for short critical sections an RW lock is often slower than a plain mutex. On this course's test machine (MinGW) std::shared_mutex was 60–400× slower than std::mutex, which is why the benchmark makes it opt-in (--rwlock). Performance portability is real.

Lock-free is not a synonym for fast

  • Lock-free: guarantees system-wide progress; an individual thread/operation may still starve
  • Wait-free: every operation completes in a bounded number of its own steps (rare, expensive)
  • Built from compare-and-swap (CAS) retry loops
  • Under contention, CAS loops retry; the cache line still bounces
  • Benefit: no convoying behind a descheduled lock holder; progress guarantees
Two hard problems

ABA: a thread reads pointer A, is delayed, another thread pops A, frees it, pushes a new node at the same address A. The first thread's CAS succeeds on a different object.

Safe reclamation: when may a node be freed if another thread may still be reading it? Hazard pointers, epochs, RCU — each with its own cost.

00:36

Say

"Lock-free changes who waits and how, not whether contention exists. On a hot key a lock-free map still funnels all threads through one cache line. Its advantages are progress and latency tails when threads are descheduled, not raw throughput."

ABA in one example

Lock-free stack: pop reads head = A and next = A->next = B, then does CAS(head, A, B). Meanwhile others pop A and B and push A again (same address, memory reused). The CAS succeeds; head now points to B, which was freed. Fixes: tagged pointers (version counter), hazard pointers, epoch-based reclamation.

Why reclamation is the hard part

In a garbage-collected language, "is anyone still reading this node?" is answered by the GC. In C++ you must implement that answer yourself. Most bugs in published lock-free C++ code are reclamation bugs.

00:45

Ask

"Your service has 90% reads and a hot key receiving 40% of traffic. Which design?" Expected: none of the locking designs fixes the hot key; fix the workload or the data: cache the hot value per thread (read-mostly replicas), split the hot key into sub-counters (sharded counter), batch updates, or make the hot entry immutable and swap it atomically (Lecture 9). Data-structure choice cannot beat a skewed workload by itself.

Other angle

Many high-performance servers avoid sharing entirely: each core owns a partition of the data and requests are routed to the owning core (shared-nothing, e.g. Seastar-style designs). Mention as the extreme point of sharding.

00:55

Say

"Big-O counts operations; the hardware charges per cache line and per miss. A DRAM miss costs as much as ~100–300 simple instructions. Designs that touch fewer lines, in predictable order, win — often by more than any asymptotic improvement."

Coherence in one sentence

When one core writes a line, every other core's copy is invalidated; the next reader must fetch it from the writer's cache (~tens of ns, more across sockets). A lock word or counter written by many cores ping-pongs between them — that is "cache-line bouncing".

Hardware numbers

Sizes are for the i7-11800H used for the measurements; latencies are typical orders of magnitude. Ask students to look up their own CPU's cache sizes (lscpu, CPU-Z) before interpreting the locality benchmark.

01:03

Read the table

With packed counters, 8 threads achieve less total throughput than 1 thread (81 vs 202 M/s), although no thread reads another thread's counter. Padding to one counter per line restores near-linear scaling (994 ≈ 4.9× one thread with 8 threads; not 8× because of turbo frequency, memory traffic and the loop itself). 12× difference from a layout change, with identical code logic.

Where false sharing hides in real code

Per-thread statistics arrays, adjacent locks (our shards are alignas(64) for this reason), a frequently written field next to a read-mostly field in the same struct, the reference count next to the data in a shared object.

Detection

Linux perf c2c reports cache lines with cross-core "HITM" traffic; Intel VTune has a memory-access analysis. Or: the symptom "adding threads makes it slower although nothing is shared".

Caveat

C++17 offers std::hardware_destructive_interference_size instead of hard-coding 64; support varies. Some CPUs prefetch adjacent line pairs, so 128 bytes can be needed.

01:10

What exactly is measured

Summing n int64 values: identical O(n) logical work in every column. The list columns use the same node pool; only the order in which nodes are linked differs (memory order vs shuffled). So the difference between the two list columns is pure access-pattern cost, not "lists are slow".

Read it

  • Small n (fits in L1/L2): all layouts are within ~3×.
  • Random pointer chasing beyond the caches: 121 ns per element — every hop is a DRAM miss, and the next address is unknown until the current load finishes (no parallelism, no prefetching). 130× slower than the vector.
  • A list in memory order is only ~2.5× slower than a vector even at 4M elements: the prefetcher follows sequential addresses through the pointers. Allocation order and fragmentation therefore change the speed of the same data structure over a program's lifetime.
  • AoS vs SoA: reading one field of a 64-byte struct loads 8× more lines than a dedicated array; the gap grows once data leaves the cache (4.5 vs 1.3 ns).

Connect back

Lecture 2 (node-based vs flat hash maps), Lecture 4 (pointer tries vs sorted arrays), Lecture 9 (path copying pays pointer chasing): this table is the mechanism behind all three.

Allocation, fragmentation, skew, NUMA

  • Allocation: every node insert calls the allocator; general-purpose allocators may lock or bounce shared metadata under threads
  • Fragmentation: long-running processes scatter nodes → locality decays; memory is "free" but unusable
  • Mitigations: pools/arenas, per-thread caches (tcmalloc, jemalloc, mimalloc), flat layouts
  • Hot keys / skew: sharding spreads keys, not load
  • NUMA (multi-socket): memory attached to the other socket is slower; a structure allocated by one thread and used by all can bottleneck on one memory controller
  • Memory bandwidth: scanning structures saturate it long before all cores are busy

01:17

Allocator story

Swapping the system allocator for a thread-caching one (jemalloc/tcmalloc/mimalloc) frequently changes multi-threaded benchmark results by 2× for node-based containers — without changing a line of the data structure. That is a confounder: report which allocator you used.

NUMA, conceptually

On two-socket servers, "first touch" decides where a page lives. A table initialised by one thread lives on that socket; threads on the other socket pay remote latency and cross-socket coherence for every access. Solutions: partition data per socket, initialise in parallel, pin threads. Students' laptops are single-socket — mention only.

Amdahl-style reasoning

If a fraction s of the work is serial (e.g. inside one lock):

speedup(N) ≤ 1 / (s + (1 − s)/N)

  • s = 10% → at most 10×, however many cores
  • s = 25% → at most 4×
  • Contention makes s grow with N → the curve bends down
serial sN = 8N = 32N → ∞
1%7.5×24.4×100×
10%4.7×7.8×10×
25%2.9×3.7×4×

Say

"Amdahl gives an upper bound when the serial part is constant. A contended lock is worse than constant: the time to hand the lock over grows with the number of waiters. That is why the global-lock curve in our experiment goes down, not flat."

Use it for estimation

If a profile shows 20% of time inside a global lock at 1 thread, you know before any experiment that the service cannot exceed 5× regardless of cores — so the lock must go before buying bigger machines. (Universal Scalability Law adds a coherence term that captures the downward bend; mention the name only.)

Throughput vs latency

Under contention, throughput may still rise slowly while p99 latency explodes, because some requests queue behind many others. Report both.

01:55

Explain each observation

  • Global lock declines: every operation needs the one lock line; handing it between cores costs more than the tiny critical section. More threads = more handoffs = less work done.
  • Sharded is far from linear: 10% writes, hashing, memory traffic of 100k-key maps, and turbo frequency dropping with more active cores. 8 threads ≠ 8× work capacity.
  • Hot key: 90% of operations take shard 0's lock. Sharding spreads keys, not load — the workload defeats the design (Lecture 3's lesson in a new form).
  • 1 thread: sharding costs an extra hash and a larger cache footprint (64 maps). Sophistication is not free when there is no contention.

Portability finding (tell students)

Adding --rwlock measures std::shared_mutex. On this MinGW build it ran at 0.1–0.6 M ops/s — 60–400× slower than a plain mutex, even for 90% reads. On Linux/glibc it behaves very differently. A performance conclusion about "RW locks" from one platform does not transfer.

02:20

Say

"Tests of concurrent code find bugs by making unlikely interleavings likely. Low contention (many keys, few threads, fast machines) makes them unlikely again. Production hot keys create the contention your test setup lacked."

Techniques, with limits

  • Stress tests with invariant checks: sum of counts = operations performed. Make contention high on purpose (few keys, more threads than cores, random sleeps/yields).
  • Repeated randomized runs: increase probability, not certainty.
  • ThreadSanitizer (-fsanitize=thread, Linux/macOS with GCC/Clang): finds data races that actually happen in the run, with low false positives; blind to atomicity violations and to races on paths not executed. Not available with this MinGW toolchain — say so.
  • Deterministic testing / model checking (e.g. controlled schedulers, CHESS-style tools, Loom in Rust): explore interleavings systematically for small tests — powerful, limited to small state spaces.
  • Reproduction: log thread ids and operation sequences; record seeds; a failure you cannot reproduce is a failure you cannot fix.

How to argue a concurrent design is correct

  1. State the invariants and which lock protects each piece of data
  2. Make compound operations atomic in the API
  3. Keep critical sections small and lock order fixed
  4. Prefer immutability and ownership transfer to sharing
  5. Test under forced contention; run sanitizers where available
  6. Review: every shared variable has exactly one synchronisation story
Warning signs in a code review
  • "It's only a counter, it doesn't need a lock"
  • volatile used for thread communication
  • Memory orderings weaker than default without a written argument
  • A get followed by a put on shared state
  • "We ran it 1,000 times"

02:32

Teaching point

"For concurrent code, the argument comes first and the tests second. Tests check that the argument matches the implementation; they cannot replace it."

volatile

In C++, volatile is for memory-mapped I/O, not threads: it provides neither atomicity nor ordering. Using it for flags is a data race and UB.

Summary

  1. Concurrent correctness = invariants at every observable point, and atomic compound operations.
  2. Data races are UB; atomicity violations are API bugs that race detectors do not see.
  3. Global locks serialise and then degrade; sharding helps uniform load, not hot keys.
  4. Lock-free changes who waits, not whether contention exists — and adds ABA and reclamation problems.
  5. Cache lines, false sharing and pointer chasing can matter more than Big-O (12× and 130× today).
  6. Every number is machine-specific: report the hardware, OS, compiler and allocator.
