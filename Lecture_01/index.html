Part 1 · 00:10–00:35

A production problem:
repeated event IDs

Part 1 is discussion-heavy. Goal: students discover that "use a hash set" is the start of the analysis, not the end.

The scenario

A payments platform ingests events from 40 upstream services. Upstreams retry on timeout, so the same event can arrive more than once.

Processing a duplicate means charging a customer twice or double-counting revenue.

The ingestion team asks: "Can you give us a component that tells us whether we have already seen this event ID?"

Facts you are given

  • Peak: 50,000 events/s
  • IDs: UUIDv4 strings (36 chars)
  • Retries happen within 10 minutes
  • Service pod memory limit: 2 GiB
  • p99 budget for the check: 200 µs
Ask the roomWhat is your first design? Write it down in one line. (60 seconds)

Do not correct yet

Background if asked

This is the classic idempotency / deduplication problem in at-least-once delivery systems (Kafka consumers, webhook receivers, payment APIs). Stripe-style APIs solve a related problem with client-supplied idempotency keys stored for ~24h. Exactly-once delivery over a network is not achievable in general; systems achieve exactly-once effects via deduplication plus idempotent processing.

"Just use a hash set" — ten questions first

  1. What are the requirements? (exact? within what window?)
  2. What is the workload? (rates, duplicate ratio, key shape)
  3. Which operations matter, and how often?
  4. What are the performance constraints? (which percentile?)
  5. What are the memory constraints?
  1. What guarantees are required? (restart? replicas?)
  2. What failures are acceptable — and which are not?
  3. What does the API promise?
  4. What invariants must always hold?
  5. How will correctness and performance claims be validated?
These ten questions are the backbone of every project proposal, design document and viva in this course.

00:18 Work the first row on the board with them.

Derivation (libstdc++, 64-bit — say "approximately", these are estimates)

  • 36-char UUID in std::string: 32 B object; 36 chars exceed the 15-char small-string buffer, so a heap block of 37 B → ~48 B with allocator rounding/header.
  • Hash node: next pointer 8 + cached hash 8 + string 32 = 48 B → allocation ~64 B.
  • Bucket array: 8 B per bucket at load ≤ 1.
  • Total ≈ 48 + 64 + 8 ≈ 120 B. 30M × 120 B ≈ 3.6 GB.
  • Binary 128-bit ID: node = 8 next + 16 key (+8 hash if cached) → 32–48 B allocation incl. header, + 8 bucket ≈ 56 B.
  • Flat open addressing with 16 B slots at load 0.5: 32 B per live entry, one allocation total.
  • Bloom filter: bits per element = −ln(p)/ln(2)² ≈ 14.4 bits for p=0.001 ≈ 1.8 B.

Key teaching point

Changing the representation of the key (parse the UUID into 16 bytes) halves memory without changing the algorithm. Changing the memory layout (flat table) nearly halves it again. Changing the guarantee (probabilistic) buys 30×. Each is a different kind of engineering decision. We will study all three this semester (Weeks 2, 10, 11).

Expected objection

"Just add memory." Answer: sometimes right! But it is a cost decision that must be made consciously, and at 3× traffic growth it fails again. Also: 3.6 GB of small allocations means allocator fragmentation and long GC-like pauses when the set is destroyed or rehashed — rehash of 30M entries is a latency spike of seconds, which violates the 200 µs p99.

Which failures are acceptable?

False "duplicate"

A new event is reported as already seen → it is dropped.

Payments: a real charge is silently lost.

Missed duplicate

A repeated event is reported as new → it is processed twice.

Payments: double charge — unless downstream is idempotent.

Discuss in pairs · 3 min A Bloom filter can produce only one of these two errors. Which one? Is it acceptable here? What would you add to make it acceptable?

00:23

Expected answer

A Bloom filter has false positives only: it may say "seen" for a new ID. That is the worse error for payments (silent loss). So a Bloom filter alone is unacceptable here.

Fix: use the Bloom filter as a fast negative path: "definitely new" → process; "maybe seen" → confirm against an exact store (database unique index / key-value store). With 0.1% FP rate, only ~0.1% of new events + the true duplicates hit the slow exact check. This is a two-tier design: approximate filter + exact authority. It reappears in Week 10.

Also draw out

  • Which error is acceptable depends on product semantics, not on the data structure. For analytics page-view counting, a missed duplicate is harmless and a false duplicate is harmless too — both just skew a number by 0.1%.
  • Restart: an in-memory set forgets everything on deploy. Is a burst of missed duplicates after deploy acceptable? That is requirement #6 (guarantees). Options: persist/replay the last 10 minutes from the log on startup.

Misconception to catch

"Probabilistic means unreliable." No: its error is one-sided, bounded and tunable. Unbounded, unmeasured error is unreliable.

AskWhy does the O(n) design win at n = 16? What would move the crossover point?

00:42 If you have time, run Student_Resources/recent_set_bench.cpp live now instead of trusting the table — your numbers will differ, which is itself a lesson.

Expected answers — why vector wins small

  • 16 × 8-byte keys = 128 B = two cache lines. A linear scan is a few predictable loads; the CPU prefetches and vectorises comparisons.
  • list+map does, per insert: hash computation, bucket lookup, two heap allocations (list node + map node), and on eviction two frees. Allocation alone is ~20–50 ns.
  • Pointer chasing: each hop is a potential cache miss.

What moves the crossover

Key size (strings: comparisons get costlier, hashing too), allocator quality, whether keys are hot in cache, the duplicate rate (a duplicate stops the scan early; a new key scans everything), CPU and cache sizes. Typical crossovers for scan-vs-hash are in the tens to low hundreds of elements.

What this table does NOT show (preview of Part 5)

Single run, no variance; mean only (no p99); one machine; one key type; synthetic IDs. It is an illustration, not evidence for a production decision.

Engineering consequence

Real libraries exploit this: small-size optimisations (absl::InlinedVector, small-string optimisation, Swiss tables' SIMD probing of 16 slots at once, sorted-vector "flat maps"). The best design can be a hybrid chosen by size.

Where system performance hides

Memory hierarchy

L1 ≈ 1 ns, RAM ≈ 80–100 ns. A cache miss costs ~100 comparisons. Layout often beats operation count.

Allocation

Every node = malloc + free + header bytes + fragmentation. Node-based containers pay per element.

Tail latency

Amortised O(1) hides the O(n) rehash. Users feel the p99, not the mean.

Constant factors

Hashing a 36-byte string costs more than comparing two integers ten times.

Concurrency

A shared structure behind one lock serialises all cores.

Input distribution

Skew, adversarial keys, sorted input — "expected" assumes a distribution.

00:48

Numbers worth quoting (order of magnitude, modern x86)

L1 hit ~1 ns (4 cycles), L2 ~4 ns, L3 ~10–15 ns, DRAM ~80–100 ns, malloc/free pair ~20–60 ns, mutex uncontended ~20 ns, contended ~µs, SSD read ~20–100 µs, same-datacenter network round trip ~0.5 ms.

Tail latency example

A hash set growing from 16M to 32M entries rehashes 16M entries in one call: easily 0.5–1 s. Amortised cost per insert is tiny; the one unlucky request that triggers it times out. Mitigations: reserve up front, incremental rehash (Redis does this: it keeps two tables and migrates a few buckets per operation), or bounded-size structures.

A data structure as a software product

A product has users who cannot read its internals. What do they need?

  • An API that is hard to misuse
  • A contract: what is promised, what is not
  • Defined failure behavior they can observe and handle
  • Evidence: tests and benchmarks they can re-run
  • Documentation of limits and assumptions
  • Stability: internals can change without breaking them
Ask You are the on-call engineer. At 03:00 the dedup component is suspected of dropping payments. What would you want it to have been built with?

00:53

Expected answers to the on-call question

  • Metrics: count of duplicates detected, entries, evictions, early evictions, memory.
  • A way to ask "was this ID seen, and when?" — i.e. debuggability.
  • Deterministic behavior: replaying yesterday's log gives the same decisions (so time must be an input, not read from the wall clock inside — we will see this in the exercise).
  • Clear documentation of what the component does not guarantee (e.g. dedup lost across restarts).
  • Logs on degraded mode ("memory limit reached, evicting early").

Point

Observability is a data-structure concern: counters must be maintained inside operations, and some designs make them cheap (a size field) while others make them expensive (counting a Bloom filter's contents is only an estimate).

Part 3 · 01:00–01:30

APIs, contracts, invariants
and observable errors

A first API — critique it

template <class Key>
class RecentSet {
public:
    explicit RecentSet(std::size_t capacity);
    bool add(const Key& key);          // "returns false on failure"
    bool contains(const Key& key);
    bool erase(const Key& key);
    std::size_t size();
    std::list<Key>& items();            // "for debugging"
};
Pairs · 4 minFind at least five problems. For each: who gets hurt, and when?

01:00

Expected findings (aim for all of these; reveal the rest yourself)

  1. add returning bool "false on failure": false could mean duplicate, capacity reached, or allocation failure. Caller cannot distinguish "duplicate — drop it" from "error — retry". Most serious: this is where payments get dropped.
  2. contains is non-const: is it allowed to change state (e.g. refresh recency)? Name and constness must tell the truth about side effects.
  3. size() non-const and not noexcept: cannot be called on a const reference; minor but signals carelessness.
  4. items() returns a mutable reference to internal representation: callers can break invariants (push a key into the list without the map), and the implementation can never change from std::list. "For debugging" APIs become production dependencies (Hyrum's Law).
  5. Capacity 0: unspecified.
  6. Eviction is invisible: caller cannot learn which key was evicted (needed for metrics or to spill to a second tier).
  7. Duplicate semantics unspecified: does re-adding refresh the position?
  8. Thread-safety unspecified.
  9. No hash/equality customisation — custom key types cannot be used.

Hyrum's Law (quote informally)

With enough users, every observable behavior of your system will be depended on by somebody — whatever the contract says. Therefore: minimise what is observable, and specify what is.

What a contract specifies

ElementFor add(k) — one possible choice
PreconditionNone beyond a valid object (any key accepted)
Postconditioncontains(k); size() ≤ capacity(); if inserted and full, the oldest key was removed and is returned
Duplicate semanticsReported as inserted = false; position not refreshed
Complexity promiseO(1) expected, O(n) worst case (hash collisions)
Exception guaranteeStrong: if it throws (bad_alloc), the set is unchanged
Invalidation / lifetimeReturns values, never references into the structure
Thread-safetyNone; external synchronisation required

The contract is a design artifact. Write it before the implementation, and test it.

01:07

Teach the vocabulary

  • Precondition: caller's obligation. Violation = caller bug. Choose between checking (throw/assert) or documenting UB. In libraries used across teams, prefer checking at boundaries.
  • Postcondition: implementation's obligation if preconditions held.
  • Exception safety levels (C++): no-throw, strong (commit-or-rollback), basic (valid but unspecified state, no leaks), none. The reference implementation achieves strong for add by inserting into the list, then the map, and undoing the list insert if the map throws — show that code on the next slide.
  • Complexity promise: part of the contract. std::unordered_map promises average O(1), worst O(n). If you promise O(1) worst-case, you cannot switch to a design that doesn't have it.

Ownership/lifetime

Returning references or iterators into the structure creates a lifetime coupling: the caller's reference dies when the key is evicted by some other call. Classic dangling-reference bug. Returning by value (or std::optional<Key>) avoids it at the cost of a copy — a deliberate trade.

Ask

"Why not refresh the position on duplicate?" Answer: then it becomes LRU; a retry storm would keep an ID alive forever; the window would no longer mean "first seen within". Both are valid products — the point is to choose and write it down.

Revised API: make outcomes explicit

template <class Key>
struct AddOutcome {
    bool inserted;               // false => duplicate
    std::optional<Key> evicted;  // set when insertion pushed out the oldest key
};

template <class Key, class Hash = std::hash<Key>, class Eq = std::equal_to<Key>>
class RecentSet {
public:
    explicit RecentSet(std::size_t capacity);      // throws invalid_argument if 0
    AddOutcome<Key> add(const Key& k);             // strong exception guarantee
    bool contains(const Key& k) const;             // no side effects
    bool erase(const Key& k);                      // false if absent (not an error)
    std::size_t size() const noexcept;
    std::size_t capacity() const noexcept;
    void clear() noexcept;
    bool check_invariants() const;                 // O(n); tests / debug only
};

01:13

Walk through each decision and why

  • AddOutcome: the three situations are now distinguishable. Allocation failure is an exception, not a return value — it is exceptional and the caller usually cannot handle it locally.
  • evicted as optional<Key>: enables metrics ("evictions/s") and tiered designs (spill the evicted key to a slower store).
  • erase of a missing key returns false: absence is a normal outcome. Exceptions for normal outcomes make callers write try/catch as control flow.
  • Capacity 0 throws: a zero-capacity dedup set silently accepts every duplicate — dangerous. Throwing at construction fails fast, at startup, in configuration code.
  • check_invariants() public but documented as O(n) diagnostics. Alternative: keep it private and friend the test. Discuss briefly.

Alternative worth mentioning

enum class AddResult { Inserted, Duplicate, InsertedWithEviction } plus a separate way to obtain the evicted key. Or std::expected (C++23) for fallible operations. Several good answers exist; ambiguity is the only wrong one.

Representation and its invariants

order_: std::list<Key>, oldest at front
index_: unordered_map<Key, list::iterator>

Invariants

  1. size() ≤ capacity()
  2. order_ and index_ hold the same key set
  3. index_[k] points at the node holding k
  4. each key appears once in order_
  5. front of order_ = oldest first-insertion

01:18

Say

"An invariant is a statement about the representation that is true between every pair of public calls. Each public method may break it temporarily, but must restore it before returning — including when it throws."

Ask: which invariant is most likely to break during refactoring?

Expected: #3 — the iterator in the map. std::list iterators stay valid across other insertions/erasures, which is why list is used. If someone "optimises" by switching order_ to std::vector or std::deque (erase in the middle / push_front invalidates iterators), every stored iterator dangles. The compiler will not complain. Only tests (with sanitizers) will.

Ask: how would a test detect a broken invariant?

Call check_invariants() after every operation in randomized tests. It walks the list and verifies each map entry points to the right node. That is O(n) — fine in tests, not in production. In debug builds you can assert(check_invariants()) at the end of each mutator.

Memory cost of this representation (connect to Part 1)

Per key: list node (2 pointers + key) + map node (next + key copy + iterator + hash) + bucket = the key is stored twice. An alternative stores the key once in the map and has the list hold pointers to map nodes, or uses an intrusive list. Engineering is choosing which cost to pay.

01:23

Heuristic to teach

Return values for outcomes the caller must routinely handle; exceptions (or std::expected) for conditions the caller usually cannot handle locally; asserts for internal bugs; counters/metrics for degradations that are acceptable but must be visible.

Degraded mode is the MSc-level idea here

The time-window version has a max_entries safeguard. When traffic exceeds the design, it must choose: (a) reject new events (back-pressure), (b) evict early (may miss duplicates), (c) grow (may OOM-kill the pod and lose everything). Option (c) is the default behavior of "just use a hash set". The reference code picks (b) and exposes early_evictions() so dashboards can alert.

02:05

Recommended answer for this scenario

"First seen within W = 10 min, with a hard cap sized to the memory budget, early eviction counted and alerted, time injected by the caller". This is RecentWindow in Instructor_Only/Lecture_01/recent_window.hpp (tests in recent_window_test.cpp); release it after class.

Why first-seen rather than last-seen: the requirement is about retries of one original event within 10 minutes of its first arrival; extending on every duplicate lets a buggy upstream retrying forever pin entries indefinitely.

Representation of the recommended answer

  • unordered_map<Key, Time> for membership + a deque<(Time, Key)> in arrival order.
  • Because now is non-decreasing, expired entries are always at the deque front → expire by popping the front while front.time + W ≤ now. Amortised O(1) per call (each entry is pushed and popped once). But one call after a long idle gap may pop millions — a latency spike. Mitigation: bound the work per call (expire at most k entries per call) — another trade-off.
  • Invariants: map and deque hold the same keys; deque times non-decreasing; no entry older than W after any call; size ≤ cap.

Memory at peak and at 3×

30M × (map node ~56 B with binary key + deque entry 24 B + bucket 8 B) ≈ 2.6 GB — over budget with a node-based map! Options: binary keys in a flat open-addressing table (~1 GB), or a smaller exact window + Bloom tier. At 3× peak the cap engages. This is a genuinely hard problem; praise teams that noticed it.

Debrief: design decisions that make testing possible

// Time is an input, not read inside.
bool seen_or_insert(const Key& k,
                    Time now);

// Test: no sleeping, fully deterministic
RecentWindow<int> w(10s, 100);
auto t0 = Time{};
assert(!w.seen_or_insert(7, t0));
assert( w.seen_or_insert(7, t0 + 9s));
assert(!w.seen_or_insert(7, t0 + 10s));
  • Injected time → deterministic tests, replayable production logs.
  • Half-open window [t, t+W) stated in the contract, tested at the boundary.
  • Non-decreasing time is a precondition — checked, not assumed.
  • Counters (early_evictions()) make degradation testable, not just loggable.

  1. Boundary: exactly at t+W (off-by-one in < vs ≤ is the most common bug).

Key ideas

  • Differential testing: run the same random operation sequence on the real implementation and a reference model; compare every result. Use a small key space (e.g. 12 keys) so duplicates, evictions and erasures happen constantly — uniform 64-bit keys would never collide and would test almost nothing.
  • Fixed seed: a failure must be reproducible. Print the seed/trial/step on failure (the test file does).
  • Shrinking (property-based testing tools like RapidCheck do this): reduce a failing sequence to the minimal one. Mention; not required.

Optional live demo (3 min)

In recent_set.hpp, change order_.push_back(k) to order_.push_front(k) and run the tests. The contract tests and the differential test both fail and print the trial. Revert.

Misconception

"Code coverage 100% means tested." Coverage says lines ran, not that the results were checked, nor that the interesting states (full, one-below-full, after erase then add) were reached.

It shows

It does not show

Threats to validity (expected answers)

  • Single run → repeat ≥ 10 times, report median and spread (IQR or 95% CI).
  • Mean hides tails → time individual ops (or batches) and report p50/p99/p99.9.
  • Unrepresentative keys → use real UUID strings or a trace.
  • Warm-up / frequency scaling / other processes → warm-up iterations, pin CPU governor, quiet machine, report the machine.
  • Dead-code elimination → the harness sums results into a checksum and prints it; show them that line.
  • Construction time excluded / included → state what is timed.
  • Small n → the design target is 30M; measure there, or explain why you can extrapolate.

Maintainable means a newcomer can…

  • find the invariants and where they are checked

Summary

  1. A structure's name is not a design. Semantics, workload and constraints come first.
  2. Asymptotic cost ≠ system cost: layout, allocation, tails and constants decide at real sizes.
  3. An API is a set of promises: outcomes explicit, errors classified, internals hidden.
  4. Invariants are how you keep a representation correct — and how tests find corruption early.
  5. Design for testability: inject time, keep a reference model, expose counters.
  6. Every benchmark comes with what it shows and what it does not.
