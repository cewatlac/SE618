Where we are

  • L5: an index is precomputed work, paid for on writes
  • Today: the purest form of that trade — how much to precompute for range aggregates, given how often the data changes

You have all seen Fenwick and segment trees. We will not re-derive them. We will ask when each one is worth deploying — including when none of them is.

Today's distinctive lesson There is no universally best range-query structure. The representation follows from the query/update ratio, operation types, data size, mutability, memory, latency and required guarantees — and from the cost of getting it wrong.

Part 1 · 00:00–00:20

Scenario: a metrics dashboard

The scenario

A monitoring service keeps, per metric series, one value per minute for a year: 525,600 buckets (requests, errors, bytes). 20,000 series.

Dashboards ask:

  • total requests between two times (sum)
  • number of error minutes (count)
  • worst p99 latency in a window (max)

Late events correct single buckets; a nightly job occasionally backfills a whole range.

Pairs · 4 min Do NOT name a data structure. Write the operation profile: which operations, what ratio, what sizes, what latency, what memory.

00:03

Expected profile (build it on the board)

  • Operations: range sum, range count (a sum of 0/1 indicators), range max, point update (correction), range update (backfill).
  • Ratio: dashboards refresh every 30 s for many viewers → queries dominate; corrections are rare for old buckets but frequent for the most recent minutes (late events arrive within minutes).
  • Sizes: n = 525,600 per series; 20,000 series → 10.5 billion buckets. Memory per series matters: 8 bytes × n = 4.2 MB; any 2× structure doubles 84 GB to 168 GB.
  • Latency: dashboard panel < 100 ms including many series.
  • Mutability: old data is effectively immutable; only the recent tail changes.

Teaching point

"The last bullet is the insight that changes everything: this is not one workload. Old data is static; the tail is dynamic. A good design may treat them differently." Keep this for the debrief.

"Each row is a property of the workload, not a property of a structure. This is the inversion we want: read left to right, never right to left."

Rollups

Real monitoring systems (Prometheus-style stores, time-series databases) mostly answer range queries with pre-aggregated rollups: per-minute, per-hour, per-day totals. A query over a week sums 7 daily values plus a few partial ends. That is a two-level prefix structure chosen for storage cost, not a textbook tree. Mention it so students see that the "answer" in industry is often not in the DSA textbook.

Part 2 · 00:20–01:00

Four representations,
one question

Scan and prefix sums: the two extremes

Scan

for (i = l; i < r; ++i) s += a[i];

query O(r − l) · update O(1) · memory n

Sequential memory: ~0.5–1 ns per element. n = 1,000 → well under a microsecond.

Prefix sums

p[k] = a[0] + … + a[k−1]
sum[l, r) = p[r] − p[l]

query O(1) · update O(n) · memory n + 1

Only works for invertible operations (sum, xor), not min/max.

AskA prefix-sum array serves 10,000 queries/s. One correction per second arrives for a random bucket. What happens?

00:20

Answer

Each correction rewrites on average n/2 = 262,800 entries ≈ 0.1–0.3 ms. One per second is fine: ~0.03% of a core. But corrections concentrate at the end (recent minutes) — then the suffix to rewrite is tiny and prefix sums are cheap! Corrections to the start of the year would be the expensive case. The distribution of update positions matters, not just their count.

Contrast with the scan

A year-long sum scans 525,600 values ≈ 0.3–0.5 ms. For one query that is fine; for a dashboard with 200 series × 10 panels refreshing every 30 s it is not. The scan's problem is throughput, not single-query latency.

Fenwick tree: logarithmic both ways, for invertible aggregates

// t[k] covers a[k - lowbit(k), k)  (1-based k)
Value prefix(size_t r) const {        // sum of a[0, r)
    Value s = 0;
    for (size_t k = r; k > 0; k -= k & -k) s += t_[k];
    return s;
}
void add(size_t i, Value delta) {
    for (size_t k = i + 1; k < t_.size(); k += k & -k)
        t_[k] += delta;
}
  • query and update O(log n); ~15 lines
  • O(n) construction is possible (ours does it)
  • Natively adds. Our contract assigns → keep a copy of a[] to compute the delta → 2n memory
  • Efficient for invertible prefix-style aggregates such as sums; not a general solution for arbitrary dynamic range-min/max

00:30

Teaching point — the contract costs memory

"The API said set(i, v) assigns. Fenwick only knows how to add. To assign you need the old value: either store a copy of the array (2n memory, our choice) or compute a[i] = query(i, i+1) in O(log n) per set (no extra memory, slower). A one-word decision in the API — 'set' vs 'add' — doubled the memory. At 10.5 billion buckets that is 84 GB."

Ask

"Which is the better API for the metrics system: set or add?" Expected: late events naturally add to a bucket (another request arrived); corrections of a wrong value assign. Both exist; a system might expose add and implement assignment rarely. Good API design follows the domain.

Don't

Don't derive lowbit or prove correctness — they know it. If a student asks, k & -k isolates the lowest set bit (two's complement).

Segment tree: the general tool

  • Any associative operation with an identity (a monoid): sum, min, max, gcd, "count and max"
  • query and update O(log n); iterative version is compact
  • Range updates via lazy propagation (extra array, harder code)
  • Memory 2n (iterative) to 4n (recursive)
Static data and min/max only? A sparse table answers range-min in O(1) after O(n log n) preprocessing — memory n·log n (20× at n = 10⁶). Immutable data only.

00:38

Say

"Segment trees are the Swiss-army knife. That generality is exactly why they are over-used: you pay for a knife you do not need when the operation is a sum and the data never changes."

Lazy propagation (conceptual)

A backfill "add 5 to every bucket in [l, r)" would be O(n log n) with point updates; lazy propagation stores pending updates on internal nodes and pushes them down only when needed → O(log n) per range update. Cost: a second array and code that is notoriously bug-prone (forgetting to push). Alternative for rare backfills: rebuild in O(n). Measure how rare "rare" is.

Sparse table

Mention only. It is the "prefix sums of min": maximal precomputation for static data, O(n log n) memory. For the metrics system's old, immutable data it is a candidate for range-max; for the live tail it is useless.

Part 3 · 01:00–01:30

One interface, four implementations

The same contract behind every representation

Callers depend on the contract; the representation can change as the workload changes — if the contract did not leak it.

01:00

Say

"This is the most important slide today. Because the four share one contract, the representation becomes a deployment decision you can revisit with evidence, instead of an architectural commitment."

Ask: how could the contract leak the representation?

Expected: exposing prefix(r) (only natural for prefix/Fenwick); promising O(1) query in the docs; returning a reference into internal storage; supporting min on the interface (excludes prefix/Fenwick); a data() accessor. Each one freezes the choice.

C++ design note

We used four concrete classes with the same member functions (compile-time polymorphism via templates in the benchmark). A virtual interface would allow runtime selection at the cost of an indirect call per operation (~1–2 ns — irrelevant for the naive scan, visible for prefix sums). Another decision with a measurable cost.

Range semantics are a contract, not a detail

QuestionOur decision

Why half-open
  • [a, b) + [b, c) = [a, c): windows compose without ±1
  • Length is r − l; empty range is natural
  • Matches C++ iterators and most time-series APIs ([start, end))
A dashboard that sums [09:00, 10:00] and [10:00, 11:00] inclusively double-counts the 10:00 bucket.

01:07

Teaching point

Off-by-one errors in range APIs are among the most common production bugs, and they are silent: totals are slightly wrong. The fix is a contract decision, documented and tested at the boundaries (our range_test.cpp tests l == r, r == n, l > r).

Invalid ranges: throw or clamp?

Ask: "A dashboard asks for [now − 1h, now + 5min) — the end is in the future. Throw or clamp?" Good answer: the data structure should be strict (throw) because it cannot know intent; the service layer above it may clamp and report the effective range to the user. Put leniency at the boundary with the most context.

Overflow

int64 sums of byte counters: 10¹² bytes per minute × 525,600 minutes ≈ 5 × 10¹⁷ — fits in int64 (9.2 × 10¹⁸) with only ~18× headroom. Bytes per second over 10 years may not. Options: document the bound, check with __builtin_add_overflow, use 128-bit, or saturate. Silent wrap-around in C++ signed arithmetic is undefined behaviour — a real correctness risk.

Mutation and concurrency

  • Dashboards read while corrections write. Our classes are not thread-safe.
  • A Fenwick set touches ~log n cells; a reader in between sees a torn state — a total that never existed
  • Prefix-sum update rewrites a suffix: a long window of inconsistency
Options
  • Reader-writer lock: simple; writers block readers
  • Immutable snapshot + atomic swap: rebuild, publish a new pointer; readers never block
  • Split by mutability: immutable history (prefix sums) + small mutable tail (Fenwick or scan)

01:18

Say

"Lecture 11 goes deep on concurrency. Today the point is that mutability is not free even when the complexity table says O(log n): every mutable structure needs a synchronisation story, and immutable ones get it almost for free."

The hybrid design (answer to Part 1's hint)

For the metrics system: buckets older than an hour are immutable → store as prefix sums (O(1) queries, no locks, cheap to persist). The last hour (60 buckets) is mutable → a plain array scanned in < 100 ns, or a tiny Fenwick. A query [l, r) splits into a prefix-sum part and a scan part. Periodically fold the tail into the history (a rebuild of one suffix). This design beats every single-structure answer on memory, simplicity and concurrency — and it is only visible if you looked at the workload first.

Anti-patterns to avoid in your justification

Weak
  • "Segment tree is better because it is O(log n)."
  • "Prefix sums are O(1), so they are the fastest."
  • "The naive version is O(n), so it does not scale."
Strong
  • "At 1% updates, prefix sums spend more time updating than querying; Fenwick bounds both at ~50 ns and costs one extra array, which fits our 4 GB budget."
  • "For n = 1,000 a scan takes well under a microsecond; we choose clarity and zero review risk; we would revisit if this moved onto a hot path."

02:10 Run ./bench live (10–20 s). Compare with the class vote on the board.

Read it row by row

  • A: prefix sums lose because the 1% of updates cost ~0.17 ms each on average: 200 updates dominate 19,800 O(1) queries. Fenwick wins; the segment tree is 2.4× slower than Fenwick for the same big-O (more memory traffic, more work per level).
  • B: prefix sums are now worse than naive. Fenwick wins by three orders of magnitude.
  • C: no updates → prefix sums win at 16 ns. The "sophisticated" segment tree is the slowest non-naive option (224 ns; this run also seems noisy — one run, remember).
  • D: everything is under 100 ns. Fenwick is 4× faster than naive, but 70 ns per operation is irrelevant for a config service. Simplicity wins unless this is on a hot path.

Answer to the lecture question

The sophisticated structure earned its complexity only for dynamic data at large n (A, B, E). For static data a simpler precomputation won; for small data, no structure was needed.

What this benchmark does not show

  • Tail latency: prefix-sum updates are an O(n) spike on the write path; means hide it
  • Update position distribution: recent-bucket corrections make prefix sums cheap
  • Range length distribution: dashboards mostly ask for recent, short windows
  • Memory at scale: 20,000 series × 2n
  • Concurrency and synchronisation cost
  • Range max, range updates, lazy propagation
  • Variance: one run per cell (look at C's segment-tree number)
  • The hybrid design (immutable history + mutable tail)
AskWhich missing measurement is most likely to change the decision for the metrics system?

Expected answer

The update position distribution. Our benchmark updates random positions; the real system updates the most recent minutes. With tail updates, prefix sums' O(n) becomes O(distance from the end) ≈ tiny — prefix sums (or the hybrid) might win for A. A benchmark whose workload does not match the system can reverse the conclusion. Second: memory at 20,000 series.

Summary

  1. Write the operation profile before naming a structure.
  2. Scan, prefix sums, Fenwick and segment trees are points on a precompute-vs-update curve.
  3. Big-O is two rows of an eight-row cost table: memory, code risk, generality and concurrency decide too.
  4. One contract, many representations: keep the contract from leaking the choice.
  5. Range semantics (half-open, 0-based, invalid ranges, assign vs add, overflow) are contract decisions.
  6. Often the best design splits the data by mutability.
