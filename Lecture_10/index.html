Part 1 · 00:00–00:20

Scenario: a crawler that
cannot remember everything

The scenario

A web crawler fetches pages and extracts links. Before fetching, it must skip URLs it has already fetched.

  • 1 billion URLs seen so far; ~80 bytes each
  • Frontier workers check 200,000 URLs/s
  • An exact set on disk: ~0.1–1 ms per lookup (too slow)
  • An exact in-memory set: ~100+ GB (too big per worker)
  • Fetching a URL twice wastes bandwidth; skipping a new URL loses a page
Pairs · 3 min Which is worse for this product: re-fetching a known URL, or never fetching a new one? What about for a payment-deduplication service?

00:03

Expected answers

  • Crawler: a duplicate fetch costs a little bandwidth; a skipped new page is lost coverage — usually worse, but a small loss (0.1–1%) may be acceptable if pages are re-discovered later via other links.
  • Payments (Lecture 1): skipping a genuine payment is unacceptable; a duplicate is also unacceptable. Neither error is free — the probabilistic structure can only be a fast pre-filter in front of an exact check.

Arithmetic

10⁹ × 80 B = 80 GB of strings alone; with hash-set overhead > 150 GB. A Bloom filter at 1% FP needs ~9.6 bits per element: 1.2 GB. At 0.1%: ~1.8 GB. Two orders of magnitude.

Teaching point

"The same structure is acceptable in one product and dangerous in another. The data structure has no opinion; the product does."

Part 2 · 00:20–01:00

Bloom filters: mechanism
and parameters

Mechanism

  • add: set k bits chosen by k hash functions
  • query: all k bits set → "maybe"; any bit 0 → "definitely not"
  • No false negatives (if nothing clears bits)
  • False positives: other keys set those bits

00:20

Say

"Everyone has seen this diagram. The interesting sentence is the asterisk on 'no false negatives': it holds only while nothing clears bits, the hash functions are the same at insert and query time, and the filter was not lost or corrupted. Those are operational conditions, not mathematical ones."

k hash functions in practice

Computing k independent hashes is expensive. Standard trick (Kirsch–Mitzenmacher): g_i = h1 + i·h2 from two hashes. Double hashing is a standard practical technique that can provide essentially the expected Bloom-filter behaviour under suitable hash assumptions — validate the actual implementation empirically, as the lab does (observed 0.99–1.01% vs 1.00% predicted). The hash quality lessons of Lecture 2 apply: a weak hash on structured keys (sequential IDs) clusters bits and raises the FP rate above the formula.

The false-positive rate, interpreted

After n insertions into m bits with k hashes:

p ≈ (1 − e−kn/m)k

  • e−kn/m ≈ fraction of bits still 0
  • p ≈ (fraction of bits set)k
  • Best k = (m/n) ln 2 → half the bits set
  • Plan: m = −n ln p / (ln 2)²

00:28

Teach interpretation, not memorisation

  • "p is the probability that k random bits are all set." If half the bits are set and k = 7: 0.5⁷ ≈ 0.8%. That one sentence explains the formula.
  • Size independence: an 80-byte URL and an 8-byte ID cost the same 9.6 bits at 1%. That is why the savings are so dramatic for large keys.
  • The optimum leaves the filter half full; the fill ratio is therefore the natural health metric.

Ask

"You need p = 0.1% instead of 1% for the crawler. How much more memory?" Answer: 14.4/9.6 = 1.5× (1.2 GB → 1.8 GB). "Is that worth it?" — depends on what a false positive costs. That is today's question in miniature.

Numbers

Teaching points

  • Degradation is non-linear: the exponent k amplifies the fill.
  • A filter at 10× capacity says "maybe" to almost everything — for the crawler, that means "skip almost every new page", silently. Silent degradation again (L3's buggy LRU, L5's stale statistics).
  • Monitoring: export the fill ratio and alert at, say, 0.6 (≈ 3% FP). Estimating n itself is possible from the fill ratio: n ≈ −(m/k) ln(1 − fill).

Mitigations

Over-provision; rebuild bigger from the source of truth; scalable Bloom filters (add a new, larger filter when one fills up, query all); time-partitioned filters (one per day, drop old ones) — which also gives a form of deletion.

Choosing k is a trade-off too

  • Too few hashes: each check is weak
  • Too many: the array fills up faster
  • Every hash is a memory access: k = 7 means 7 likely cache misses per query for a large filter

Blocked Bloom filters put all k bits of a key in one cache line: slightly higher p, far fewer misses.

00:44

Say

"Notice the parallel with Lecture 11 next week: the textbook optimum minimises FP rate; a production optimum may accept a slightly higher p to get 1 cache miss per query instead of 7. Blocked Bloom filters (e.g. in RocksDB's newer filter format) make exactly that trade."

Misconception

"More hash functions = more accurate." True only up to the optimum; past it, accuracy gets worse (k = 20: 7% vs 1%).

Contract of a Bloom filter

void add(uint64_t key);
bool might_contain(uint64_t key) const;   // false: definitely never added
                                          // true: added, or a false positive (~p)
double fill_ratio() const;                // monitoring: current p ≈ fill^k
bool merge(const BloomFilter& other);     // union; only if m, k, seed are equal
  • The name might_contain encodes the semantics; contains would lie
  • Parameters (m, k, hash, seed) are part of the persisted format and of mergeability
  • No remove: clearing a bit may create false negatives for other keys

00:52

API naming

Guava's API is literally mightContain. Names that tell the truth protect callers — Lecture 1's contract lesson.

Merge

Union of two filters with identical parameters = bitwise OR. This makes Bloom filters naturally distributed: each worker builds a filter over its partition, then OR them. Intersection is also possible (AND) but its FP rate is worse than a filter built from the intersection.

Persistence

A filter is just bits: easy to snapshot. But the hash function and seed must be versioned with it; changing the hash library silently turns every stored filter into garbage (every query becomes a random answer — including false negatives). That is an operational failure mode worth a test.

Part 3 · 01:00–01:30

Error budgets, placement, danger

Placement: a filter in front of the truth

01:00

Say

"This is the most common production pattern: the probabilistic structure is not the source of truth, it is a filter that avoids expensive work. LSM storage engines (RocksDB, Cassandra, HBase) keep a Bloom filter per on-disk file so that a lookup skips files that cannot contain the key. With p = 1%, 99% of pointless disk reads disappear, and correctness still comes from the files."

Cost model

Expected cost per lookup of a new key = filter check + p × exact lookup. With a 1 ms disk lookup and p = 1%: ~10 µs on average instead of 1 ms. Now 'is p = 1% acceptable?' has a numeric answer: it sets the load on the exact store.

01:06

Say

"Same structure, same p. The only thing that changes down the table is what a 'maybe' does. When the action on a false positive is irreversible, security-relevant or financial, the filter may only be used to avoid work, never to decide."

Ask

"Could a Bloom filter be safe for authorisation if it stored the denied users instead?" Then a false positive denies a legitimate user (annoying, safe) — the direction of the error flips with what you store. Good design question: choose what the set contains so that its error is the harmless one.

Adversarial inputs

If attackers can choose keys and know the hash function, they can craft keys that are false positives (e.g. URLs that the crawler will always skip), or fill the filter with junk to raise p for everyone. Defences: keyed/secret hash seeds (Lecture 2), rate limits on insertions, monitoring the fill ratio.

Deletion, saturation, distribution

  • No deletion: clearing a bit can create false negatives for other keys
  • Counting Bloom filter: small counters instead of bits (≈4× memory); deletion becomes possible — deleting a key that was never added corrupts it
  • Time-partitioned filters: one per day; "delete" = drop old days
  • Saturation: monitor fill ratio; rebuild or add a layer
  • Mergeable: OR per-worker filters with identical parameters
  • Monitor actual error: sample "maybe" answers and verify against the exact store — the observed p is a production metric

01:12

Capacity drift in production

Filters are sized for a forecast; traffic grows; nobody resizes; p climbs from 1% to 15% over a year, and the exact store's load rises 15×. The first symptom is "the database got slower", not "the filter is full". The fix is to measure p directly: the exact store knows when a "maybe" was a false positive — count them.

Alternatives to mention

Cuckoo filters support deletion and have better cache behaviour at low p; quotient/XOR filters are more compact for static sets. Names only.

Count-Min Sketch: approximate frequencies

  • d rows × w counters; each row has its own hash
  • add(x): increment one counter per row
  • estimate(x): minimum over rows
  • With nonnegative updates it never underestimates
  • Under the standard hash assumptions: estimate ≤ true + εN with probability ≥ 1 − δ, for w = e/ε, d = ln(1/δ)
  • Error is relative to the total stream, not to the key

01:18

Rigour: theory vs our implementation

The bound (estimate ≤ true + εN with probability ≥ 1 − δ) is a theorem under the standard assumptions: pairwise-independent hash functions per row and nonnegative updates. Our implementation uses mixed, seeded 64-bit hashes; that is common practice, but it is not a proof that the assumptions hold. The demo's result (no tail key exceeded the bound) is empirical evidence about this implementation on this stream, not a verification of the theorem. With negative updates (deletions as −1), the "never underestimates" property no longer holds.

Use cases

Heavy-hitter detection (top talkers for abuse/rate limiting), network telemetry, query frequency for cache admission (TinyLFU in Caffeine uses a Count-Min-style sketch — Lecture 3), approximate joins.

Read the table

At ε = 0.01 (11 KB!) even the top-100 keys are overestimated by more than 100%: each is only ~0.1% of the stream, well below εN. Only true heavy hitters (> 1% of the stream) are reliable. At ε = 0.0001 (1 MB, still 7× smaller than exact) the top keys are within 0.2%. The error budget depends on which keys you care about.

Mergeability

Two sketches with the same dimensions and hashes add element-wise: per-server sketches can be summed centrally. That is why sketches dominate distributed telemetry.

HyperLogLog (one minute)

Counts distinct elements (unique visitors) in ~12 KB with under 1% standard error (Redis: 0.81%), mergeable across servers (Redis PFCOUNT). Mention only.

When is a probabilistic structure dangerous?

Red flags
  • The answer decides an irreversible, security or financial action
  • Nobody knows the actual n (capacity drift)
  • The error rate is not monitored in production
  • Keys are attacker-controlled and the hash is public
  • Parameters/hash can change without rebuilding stored filters
Safe patterns
  • Filter before an exact source of truth
  • Store the set whose error is harmless
  • Size for growth; alert on fill ratio
  • Count observed false positives
  • Version the parameters with the data

02:20

Intuitive uncertainty

Counting false positives is estimating a proportion. With N probes and true rate p, the standard error is √(p(1−p)/N): for p = 1%, N = 10⁶ → ±0.01 pp (so the 95% interval is about ±0.02 pp); N = 1,000 → ±0.3 pp (±0.6 pp at 95%). To measure a 1% rate to ±10% relative accuracy you need tens of thousands of probes. Rare events need big samples.

Also

Seeds vary two things: the inserted keys and the filter's hash seed. The spread across seeds is small here because each run already has 10⁶ probes. In production, the observed p also depends on the key distribution (Lecture 2: structured keys + weak hash → higher p than the formula).

Teaching point

"Never write 'the false-positive rate is X' without the sample size or an interval." The same rule applies to every benchmark in your project — Lecture 12 generalises it.

If p = 1%, is that acceptable?

It depends on what a false positive causes. Turn p into product units:

  • Crawler: 200,000 checks/s × 1% of new URLs → pages skipped per day?
  • Disk filter: 1% of misses → extra disk reads/s → is the store sized for it?
  • Payments: 1% of anything → unacceptable as a decision
Groups · 5 min The crawler discovers 50M new URLs/day. At p = 1%, how many new pages are never fetched per day? Would you pay 0.6 GB more RAM per worker to reach 0.1%?

02:32

Expected answer

50M × 1% = 500,000 new pages skipped per day (unless rediscovered). At 0.1%: 50,000. Going from 1% to 0.1% costs 1.5× memory (1.2 → 1.8 GB for 10⁹ URLs). Whether 450,000 extra pages/day are worth 0.6 GB per worker is a business decision — but it can now be made with numbers instead of adjectives.

Debrief: what students should conclude

  1. No false negatives observed — and a correct implementation should never produce one.
  2. The formula predicts the observed p well for well-mixed hashes.
  3. Capacity errors hurt non-linearly; monitor the fill ratio.
  4. Small samples mislead; always state the sample size.
  5. Acceptability is a product question, answered in product units.

If a project uses an approximate structure

Its evaluation must report the observed error rate with sample size, the planned vs actual capacity, and the product cost of an error.

Summary

  1. Probabilistic structures trade certainty for memory, bandwidth or time — deliberately.
  2. A Bloom filter's error is one-sided; p ≈ (fill)k; ~4.8 bits per element per 10× in p.
  3. Exceeding planned capacity degrades p non-linearly and silently; monitor fill and observed p.
  4. Put the approximation in front of an exact source of truth; never let it decide irreversible actions.
  5. Count-Min Sketch: never under (nonnegative updates); over by ≤ εN with probability ≥ 1 − δ under its hash assumptions — good for heavy hitters, poor for small counts.
  6. Error rates are measurements: report sample sizes and uncertainty.
