The scenario

An Egyptian e-commerce site wants suggestions in its search box.

  • 2 million suggestion strings (product names + popular past queries), Arabic and English

  • End-to-end p99 ≤ 50 ms; the suggestion lookup gets ≤ 2 ms p99

The key insight to build toward

The textbook trie argument is: "lookup costs O(|prefix|), independent of n". But for autocomplete, finding the prefix node is the cheap part. The expensive part is ranking: the prefix "s" may match 150,000 strings, and we need the 10 most popular. A plain trie must visit the whole subtree — O(size of subtree), not O(|prefix|). Short prefixes are the most common queries and have the largest subtrees.

Memory budget arithmetic

300 MB / 2M = 150 B per suggestion. The strings themselves (avg ~25 bytes UTF-8, Arabic letters are 2 bytes each) plus a score already use ~30–60 B. That leaves ~100 B for the index. Keep this number; we will measure the trie against it.

Rebuild-and-swap

With daily scores and hourly inserts, a very common production pattern is: build an immutable index offline, ship it, atomically swap a pointer. Then the structure does not need in-place updates at all — which changes which structures are acceptable (compressed, static ones become attractive).

Part 2 · 00:20–01:00

Trie design: children, terminals,
ranking, deletion, invariants

The structure, and why it needs a terminal flag

Terms: car, card, care, cat, do

  • Each edge = one symbol (byte? code point?)
  • A node = the set of terms sharing a prefix
  • Terminal (●): a term ends here. car is a term and a prefix of card — structure alone cannot tell
  • Payload on terminal: term id, score, display string

00:20

Say

"You know this. Three questions we will spend the next 40 minutes on: how are children stored, how do we rank, and how do we delete — and each has a memory or complexity surprise."

Terminal-state bug

A classic implementation bug: using "node has no children" to mean "is a word". Then car is not found once card is inserted. Another: deleting card by removing the node chain up to the root — which deletes car too. Both violate the invariant "the set of terminal nodes = the set of terms".

Symbol choice (preview of Part 3)

Edges labelled by bytes (UTF-8) give ≤ 256 children and deep paths for Arabic (2 bytes per letter). Edges labelled by code points give fewer levels but a huge alphabet (≈150k). Neither is "correct"; it is an engineering choice with memory consequences.

00:27

Numbers (64-bit, libstdc++, approximate)

  • std::map header ~48 B; each entry is a red-black tree node: 3 pointers + colour + key + value ≈ 48 B + allocator header.
  • Node count: for 2M strings of average length ~20 symbols, a trie has on the order of 10–25M nodes (shared prefixes reduce it). At ~100 B per node that is 1–2.5 GB — far beyond 300 MB.
  • Bitmap + popcount (the "HAMT"/"array-mapped" trick): a 256-bit bitmap says which symbols have children; child index = popcount of bits below the symbol. Used in hash array mapped tries and in some static tries.

Ask

"Our benchmark uses std::map. Predict the bytes per term for 200k terms." Let them guess; the measured answer is ~290 B/term on top of the strings themselves (~47 B/term). Reveal in Part 4.

Pointer-heavy consequence

Every step down the trie is a dependent load from a different heap location — a likely cache miss (~80–100 ns) once the trie exceeds the cache. A 10-character prefix = 10 dependent misses ≈ 1 µs before any ranking work. A binary search over a sorted array of 2M strings is ~21 comparisons, also with misses — the asymptotic advantage is much smaller than it looks.

Ranking: where the cost actually is

A. Walk + enumerate subtree

Find the prefix node, DFS its subtree, keep a size-k heap.

Cost: O(|p| + subtree size · log k). For "s", the subtree may hold 7% of all terms.

slowest exactly on the most common queries

B. Cache top-k in every node

Each node stores the ids of the k best terms beneath it.

Query: O(|p| + k). Memory: + up to k ids per node. Score update: fix every ancestor, O(|term| · k).

fast reads, costly memory and updates

AskWith the sorted-array design, is the problem any different? What would "caching top-k" mean there?

00:35

Answer to the question

Same problem: the matches of a prefix form a contiguous range in a sorted array (a nice property!), but finding the top 10 in a range of 150,000 still means scanning it — unless we add a structure for "top-k in a range" (a range-maximum structure; Week 6 topic!) or precompute top-k for short prefixes only (a hash map from prefix → top-k for |p| ≤ 3; longer prefixes have small ranges and are cheap to scan). That hybrid is often the best practical design. It appears in the exercise.

Point

The data-structure question for autocomplete is not "trie vs array" but "how do we answer top-k over the set of prefix matches under our prefix-length distribution".

Update cost of cached top-k

A score change for one term must update the lists of all its ancestors (|term| nodes). If the term drops out of a node's top-k, the node needs the next best candidate — which requires information not in the cache (recompute from children). This is why many systems rebuild offline and swap.

Deletion: unmark, then prune — carefully

bool erase(std::string_view w) {                 // false if w was not a term
    std::vector<std::pair<Node*, char>> path;
    Node* n = &root_;
    for (char c : w) {
        auto it = n->kids.find(c);
        if (it == n->kids.end()) return false;
        path.push_back({n, c});
        n = it->second.get();
    }
    if (!n->terminal) return false;             // "car" may be only a prefix
    n->terminal = false;
    --size_;
    while (!path.empty() && !n->terminal && n->kids.empty()) {   // prune dead branch
        auto [parent, c] = path.back(); path.pop_back();
        parent->kids.erase(c);                   // destroys n
        n = parent;
    }
    return true;                                 // cached top-k lists on path now stale!
}

00:42

Walk through

  • Return false for "not a term" — including when w is only a prefix of other terms. Deleting a non-term is a normal outcome (Lecture 1).
  • Pruning stops at the first node that is terminal or still has children — so deleting card removes only the d node, and car survives.
  • Iterative with an explicit path: recursion depth = term length; fine here, but explicit paths avoid stack issues for pathological long keys (a URL of 8 KB).
  • Last comment: with cached top-k, every ancestor list may still contain the deleted term. Deletion is where the caching design pays — correctness now needs recomputation up the path.

Lazy alternative

Mark deleted (tombstone!) and filter at query time; purge on rebuild. Same idea as Lecture 2. Consequence: a top-10 list may now contain deleted entries, so store top-(k + slack) or fall back to DFS when too many are filtered.

Business angle

Deletion is often a compliance requirement (remove an offensive or legally problematic suggestion now). "Rebuild tonight" may be unacceptable for that path → a small blocklist checked at query time is the usual answer.

API and invariants

struct Suggestion { std::string display;
                    std::uint32_t score; };

class Autocomplete {
public:
    // Builds from raw strings; normalises internally.
    static Autocomplete build(std::span<const Entry>);
    // Up to k results, score desc, ties by
    // normalised text asc. k ≤ 50.
    std::vector<Suggestion>
        top_k(std::string_view raw_prefix,
              std::size_t k) const;
    std::size_t size() const noexcept;
};
Invariants
  1. Terminal nodes ↔ terms, one-to-one; size() = #terminals
  2. No dead branches: every leaf is terminal
  3. Children of a node have distinct symbols
  4. Cached list at node = top-k of its subtree (same order as contract)
  5. Indexed keys are normalised by the same function used for queries

00:50

API decisions to highlight

  • Immutable, built in one shot (build) — matches rebuild-and-swap; allows compact static layouts. Thread-safe for concurrent reads by construction.
  • The API takes the raw prefix and normalises internally. If callers had to normalise, some would forget → invariant 5 broken from outside.
  • Deterministic tie-break is in the contract: tests and caches (and users!) see stable results.
  • Cap on k: protects the service from k = 1e6 requests (resource exhaustion).
  • Returns display strings by value: no lifetime coupling with the index (which may be swapped out).

Invariant 5 is Lecture 2's rule 1 again

Equal-under-normalisation must mean identical keys. Index with one normaliser and query with another → misses that look like data bugs.

memory and alternatives

What is a "character"?

01:00

Key facts

  • UTF-8 is prefix-safe: if string A is a prefix of B at the code-point level, their UTF-8 encodings are byte-prefixes. So a byte-trie over normalised UTF-8 answers code-point prefix queries correctly — as long as the query does not end mid-code-point (it won't, if the client sends valid UTF-8).
  • Unicode normalisation forms: NFC (composed), NFD (decomposed), NFKC/NFKD (compatibility: e.g. "ﬁ" ligature → "fi", full-width digits → ASCII). For search keys, NFKC + case folding is a common base.
  • C++ has no standard Unicode normalisation. Use ICU (icu::Normalizer2) or a vetted library; do not hand-roll. For the course project, restrict and document the supported character set if needed — that is an acceptable engineering scope decision if stated.
  • Case folding is locale-dependent: Turkish dotted/dotless i (İ/i, I/ı). "Lowercase" is not a universal function.

Say

"For an Egyptian e-commerce site, a user typing اسكندريه must find الإسكندرية-related products. That match depends entirely on folding rules decided by the product team, not on the trie."

Discussion points

  • Folding increases recall and can reduce precision (two different words become equal). Taa marbuta folding is the most debated; decide with product/linguistic input.
  • Mixed-language strings ("iPhone ١٥ برو") need both Arabic folding and Latin case folding, and digit folding.
  • Word-prefix matching in Arabic interacts with attached prefixes (ال، و، ب): "the" is attached to the word. Matching كتاب inside والكتاب is a tokenisation decision — out of scope for today, but a good project extension.
  • Where to fold: in one function used by both the index builder and the query path; version it — changing it requires a rebuild.

Test cases to write

Idempotence (fold(fold(x)) = fold(x)); pairs that must fold equal; pairs that must stay different; display text unchanged; mixed scripts; empty string after folding (input of only diacritics).

01:12

Say

"The trie does not store the strings more compactly than the strings themselves. It stores them as a graph of heap objects, and every edge costs roughly an order of magnitude more than the byte it represents."

Tries do share prefixes — why no saving?

Sharing saves one node per shared character, but each node costs ~50–100 B while the character it replaces costs 1 B (2 for Arabic). Compression only wins when the per-node cost is tiny (packed arrays, bit-level encodings, FSTs).

Pointer-heavy structures and caches

Beyond size: nodes allocated in insertion order end up scattered; a DFS touches each at random addresses. The sorted array's range scan is sequential memory — hardware prefetchers love it. This is why the trie loses on the benchmark even for long prefixes (Part 4).

01:20

Brief notes

  • Radix / Patricia trie: collapse chains of single-child nodes into one edge labelled by a string. Node count drops from ~characters to ~branch points (≤ 2n). Implementation complexity rises: edge splitting on insert, merging on delete.
  • FST (finite state transducer): minimal automaton sharing prefixes and suffixes, with outputs on arcs. Apache Lucene's suggesters use FSTs; built offline from sorted input, very compact, immutable. Introductory mention only.
  • Ternary search tree: each node has lo/eq/hi children; memory between a trie and a BST. Mention if asked.
  • Updates in the sorted array: keep a small sorted "delta" of new items, query both and merge; periodically rebuild. This is the LSM idea (Week 9 relatives).

02:08 Run ./ac live if time permits (~20 s), or ./ac 50000 (~5 s).

Explain each row

  • Sorted array: short prefixes scan large contiguous ranges — sequential memory, fast per element (~5 ns/element), but 60 µs at |p|=1 because the range is ~10k entries. Scaled to 2M terms, |p|=1 would be ~0.6 ms — within 2 ms, but with little headroom for p99. The hybrid prefix table fixes exactly this.
  • Trie + DFS: same number of candidate terms as the array, but reached by pointer-chasing through map nodes: ~20× slower than scanning. The "O(|p|)" walk is irrelevant — ranking dominates.
  • Cached top-k: 1,000× faster than the array for short prefixes. Costs: build time, memory (and at 2M terms, ~700 MB — over budget), and hard in-place updates.

Differential check

Point at "0 mismatches": before comparing speeds, the benchmark verifies all designs return identical results for all 8,000 queries. A benchmark of implementations that disagree is meaningless.

What this benchmark does not show

  • Real strings: synthetic syllable words, ASCII only; no Arabic (2-byte letters, deeper tries)
  • Scale: 200k, not 2M; the trie may not fit in memory at 2M
  • Tail latency: best-of-3 means, no p99
  • Real memory: allocator headers and fragmentation excluded
  • Updates: build-only; no insert/re-score costs measured
  • Alternative child layouts: a packed-array trie would be far smaller and faster than std::map
  • The hybrid (array + short-prefix table) was not built

Testing and benchmarking autocomplete

Test and benchmark plan

Tests

  • Differential vs brute force: scan all terms, filter prefix, sort by contract
  • Terminal-state cases: term that is a prefix of another; delete one, the other survives
  • Empty prefix; no match; k = 0; k > matches; ties
  • Normalisation: idempotence, fold-equal pairs, must-differ pairs, mixed scripts
  • Invariants after each build/insert/delete

Benchmarks

  • Query latency by prefix length, weighted by the real length distribution
  • p50 / p99, not only means
  • Memory: counting allocator and process RSS
  • Build time and update cost (insert, re-score, delete)
  • Scale sweep: 10⁵ … 2·10⁶ terms

02:20

Emphasise

  • The brute-force oracle is ~10 lines and obviously correct; it makes every other design testable (same pattern as Lectures 1–3).
  • Weight latency by the prefix-length distribution: a design that is 10× faster at |p|=8 but 2× slower at |p|=1 is worse for real traffic. Report a workload-weighted number.
  • Use a query log if available; otherwise state the synthetic assumption (threat to validity).

Summary

  1. For autocomplete, finding the prefix is cheap; ranking the matches is the cost.
  2. Terminal state and careful pruning are what make a trie correct.
  3. Child representation determines memory; pointer-heavy tries amplify bytes 5–10×.
  4. Normalisation (Unicode, Arabic folding, case) is a product contract shared by index and query.
  5. Sorted arrays keep matches contiguous; a small precomputed table can remove their weak spot.
  6. Choose by measured memory and latency under the real prefix-length distribution.
