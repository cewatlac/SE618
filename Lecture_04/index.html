Today: a structure famous for its complexity — lookup in O(length of the prefix), independent of vocabulary size. Is that what the product needs?

Part 2 · 00:20–01:00

Trie design: children, terminals,
ranking, deletion, invariants

The structure, and why it needs a terminal flag

Terms: car, card, care, cat, do

  • Each edge = one symbol (byte? code point?)
  • A node = the set of terms sharing a prefix
  • Terminal (●): a term ends here. car is a term and a prefix of card — structure alone cannot tell
  • Payload on terminal: term id, score, display string

Child representation: the real design decision

Children stored asLookup per symbolMemory per nodeNotes
Fixed array [256] of pointers1 load2 KB (mostly null)Fast, absurd memory
Fixed array [26]1 load208 BOnly for a–z: no Arabic, no digits

Bitmap + packed child arraypopcount32 B + 4 B/childCompact, static-friendly

Most nodes deep in a trie have one child. The representation is paid for millions of times.

Ranking: where the cost actually is

A. Walk + enumerate subtree

Find the prefix node, DFS its subtree, keep a size-k heap.

Cost: O(|p| + subtree size · log k). For "s", the subtree may hold 7% of all terms.

slowest exactly on the most common queries

B. Cache top-k in every node

Each node stores the ids of the k best terms beneath it.

Query: O(|p| + k). Memory: + up to k ids per node. Score update: fix every ancestor, O(|term| · k).

fast reads, costly memory and updates

Deletion: unmark, then prune — carefully

bool erase(std::string_view w) {                 // false if w was not a term
    std::vector<std::pair<Node*, char>> path;
    Node* n = &root_;
    for (char c : w) {
        auto it = n->kids.find(c);
        if (it == n->kids.end()) return false;
        path.push_back({n, c});
        n = it->second.get();
    }
    if (!n->terminal) return false;             // "car" may be only a prefix
    n->terminal = false;
    --size_;
    while (!path.empty() && !n->terminal && n->kids.empty()) {   // prune dead branch
        auto [parent, c] = path.back(); path.pop_back();
        parent->kids.erase(c);                   // destroys n
        n = parent;
    }
    return true;                                 // cached top-k lists on path now stale!
}

API and invariants

struct Suggestion { std::string display;
                    std::uint32_t score; };

class Autocomplete {
public:
    // Builds from raw strings; normalises internally.
    static Autocomplete build(std::span<const Entry>);
    // Up to k results, score desc, ties by
    // normalised text asc. k ≤ 50.
    std::vector<Suggestion>
        top_k(std::string_view raw_prefix,
              std::size_t k) const;
    std::size_t size() const noexcept;
};
Invariants
  1. Terminal nodes ↔ terms, one-to-one; size() = #terminals
  2. No dead branches: every leaf is terminal
  3. Children of a node have distinct symbols
  4. Cached list at node = top-k of its subtree (same order as contract)
  5. Indexed keys are normalised by the same function used for queries

Two visually identical strings can have different code points: "café" as NFC (4 code points) vs NFD (5). Without normalisation, a prefix query for one misses the other.

Memory amplification: where the bytes go

Measured, 200,000 short synthetic terms (2–5 syllables):

ComponentMBB/term
The strings themselves (std::string)9.447
Sorted array index (reuses strings)00
Pointer trie, std::map children58.2291
Same trie + cached top-1070.9354

Live heap bytes via a counting operator new; allocator headers excluded — real RSS is higher.

Why so much?
  • ~1 node per character not shared with another term
  • Each node: map header + child entry node + terminal fields
  • Each child entry is its own heap allocation
Scaled to 2M terms: ~600 MB for the trie alone — twice the budget.

The plain trie — the "O(|p|)" structure — is the slowest at every prefix length and uses the most memory per useful feature. Its advantage only appears once ranking is precomputed.

What this benchmark does not show

  • Real strings: synthetic syllable words, ASCII only; no Arabic (2-byte letters, deeper tries)
  • Scale: 200k, not 2M; the trie may not fit in memory at 2M
  • Tail latency: best-of-3 means, no p99
  • Real memory: allocator headers and fragmentation excluded
  • Updates: build-only; no insert/re-score costs measured
  • Alternative child layouts: a packed-array trie would be far smaller and faster than std::map
  • The hybrid (array + short-prefix table) was not built
AskWhich one of these gaps, if closed, is most likely to change the recommendation? That is the next experiment to run.
Part 5 · 02:20–02:35

Testing and benchmarking autocomplete

Test and benchmark plan

Tests

  • Differential vs brute force: scan all terms, filter prefix, sort by contract
  • Terminal-state cases: term that is a prefix of another; delete one, the other survives
  • Empty prefix; no match; k = 0; k > matches; ties
  • Normalisation: idempotence, fold-equal pairs, must-differ pairs, mixed scripts
  • Invariants after each build/insert/delete

Benchmarks

  • Query latency by prefix length, weighted by the real length distribution
  • p50 / p99, not only means
  • Memory: counting allocator and process RSS
  • Build time and update cost (insert, re-score, delete)
  • Scale sweep: 10⁵ … 2·10⁶ terms

Weak vs strong: the same project, two proposals

Weak

"We will build a fast autocomplete using a trie because tries have O(m) lookup. We will test it with unit tests and benchmark it to show it is fast. It will support insert, delete and search."

  • Structure chosen before the problem
  • No workload, no numbers, no alternative
  • "Show it is fast": conclusion fixed in advance
Strong

"Suggestions for a 500k-product catalogue (published dataset X), Arabic + English, 2 ms p99, 150 MB. Candidates: sorted array (baseline), array + short-prefix top-k table, radix trie with cached top-k. Hypothesis: the hybrid matches the trie's p99 at < 30% of its memory; if the trie is within 1.5× memory, we choose it for in-place updates. Oracle: brute-force scan."

Summary

  1. For autocomplete, finding the prefix is cheap; ranking the matches is the cost.
  2. Terminal state and careful pruning are what make a trie correct.
  3. Child representation determines memory; pointer-heavy tries amplify bytes 5–10×.
  4. Normalisation (Unicode, Arabic folding, case) is a product contract shared by index and query.
  5. Sorted arrays keep matches contiguous; a small precomputed table can remove their weak spot.
  6. Choose by measured memory and latency under the real prefix-length distribution.
