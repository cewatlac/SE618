Lecture 5
Search Systems and Inverted Indexes

An index buys query speed with storage, build time and update complexity. Is the trade worth it?

Saturday 24 October 2026 · 3 hours
Architecture / design / API document due next Saturday, 31 Oct

Where we are

  • L2: hash maps — O(1) is conditional
  • L3: caches — the workload picks the policy
  • L4: autocomplete — ranking the matches is where the cost is

Today we generalise L4 from "prefix of one string" to "which of millions of documents contain these words?" — and we pay attention to writes for the first time.

Today's distinctive lesson An index is precomputed work. It trades storage, build time and update complexity for query latency. Whether the trade is worth it depends on the query rate, the update rate and the freshness requirement.

The scenario

An internal knowledge base (support articles, runbooks, tickets) launched with 4,000 documents. Search = "for each document, does it contain every query word?" It was fine.

Three years later:

  • 3 million documents, ~400 words each
  • 200 searches/s at peak; support agents expect results while typing
  • ~50 new or edited documents per minute
  • Search p95 has grown to seconds

Why the scan stopped scaling

Two separate problems
  • Latency: every query touches every byte of the corpus.
  • Throughput: 200 q/s × 10 s of CPU per query = 2,000 cores.
Linear growth with corpus size is fine at 4,000 documents and hopeless at 3 million.

Document ids
  • Internal ids are dense integers assigned at indexing time, separate from external ids (URLs, ticket numbers)
  • Posting lists are kept sorted by id — this is what makes intersection linear and compression effective
  • Monotonic id assignment turns insertion into an append

Boolean queries are set operations on sorted lists

// AND: linear merge of two sorted lists
std::vector<DocId> out;
std::size_t i = 0, j = 0;
while (i < a.size() && j < b.size()) {
    if (a[i] < b[j])      ++i;
    else if (b[j] < a[i]) ++j;
    else { out.push_back(a[i]); ++i; ++j; }
}
  • AND = intersection, O(|a| + |b|)
  • OR = union (merge), O(|a| + |b|)
  • AND NOT = difference
  • Multi-term AND: start with the rarest term; the result can only shrink
  • |a| ≪ |b|: gallop / skip through b → O(|a| log |b|)

Ranking, just enough

Boolean matching says which documents; ranking says which first.

  • tf — how often the term occurs in the document
  • df — how many documents contain it
  • idf = log(N / df) — rare terms carry more signal
  • score(d, q) = Σ over terms (1 + log tf) · idf

BM25 refines this with length normalisation and saturation. Not today.

Engineering consequences
  • Ranking needs tf in postings and N, df at query time
  • After deletions, df and N are wrong until they are recomputed: scores drift
  • Top-k of a union can be answered without scoring every match (WAND, block-max) — the Lecture 4 lesson again

Incremental indexing: immutable segments

  • New documents go to an in-memory buffer
  • Refresh: buffer → small immutable segment → searchable
  • Queries search all segments and merge results
  • Delete = mark in a bitmap (a tombstone, as in L2)
  • Merge: combine small segments in the background, dropping deleted docs

  3. What if the process dies halfway through an update?
  4. Is search strongly consistent with the database of record?
  5. What does false mean for each call?

Invariants of an inverted index

  1. Every posting refers to a live document
  2. Posting lists are strictly increasing by doc id: sorted, no duplicates
  3. Forward and inverted views agree: t ∈ terms(d) ⇔ d ∈ postings(t)
  4. No empty posting lists remain in the dictionary
  5. Document metadata (lengths, N) matches the indexed set
Where bugs come from
  • Update adds new postings but forgets to remove old ones → a document matches words it no longer contains
  • Re-adding an id already present → duplicate postings, double-counted tf and df
  • Removing without the forward index → dangling postings

Project: what is your index?

Five questions for your design document

  1. What is your equivalent of an index — what work are you precomputing?
  2. What maintenance cost does it introduce on every write?
  3. Are you optimising reads by making writes more expensive? Is your read/write ratio known?
  4. What consistency promise are you making — when does a change become visible?
  5. What happens after a crash — rebuild, replay, or lose data? How long does it take?

Summary

  1. A linear scan's cost grows with the corpus; an index makes cost proportional to the posting lists touched.
  2. The analyzer defines what "match" means and must be identical at index and query time.
  3. Sorted postings make AND/OR linear merges; start with the rarest term.
  4. The index is precomputed work: pay in memory, build time, update complexity and freshness.
  5. Immutable segments + merge make updates and concurrency manageable, at the cost of background work.
  6. Specify when changes become searchable, and what happens on partial failure.
