Today's distinctive lesson An index is precomputed work. It trades storage, build time and update complexity for query latency. Whether the trade is worth it depends on the query rate, the update rate and the freshness requirement.

The scenario

An internal knowledge base (support articles, runbooks, tickets) launched with 4,000 documents. Search = "for each document, does it contain every query word?" It was fine.

Three years later:

  • 3 million documents, ~400 words each
  • 200 searches/s at peak; support agents expect results while typing

00:10

Say

"The scan did nothing wrong. Its cost is proportional to the corpus, and the corpus grew 750×. The question is not 'is scanning bad?' but 'at what size, query rate and update rate does it stop being the right product?'"

Why the per-query cost is high even at 1,000 documents

Our scan re-tokenises every document on every query (lower-casing, splitting, stop-word lookup, string allocations). A scan over pre-tokenised documents would be faster — but notice that "pre-tokenised documents" is already a forward index: precomputation has started to creep in. Plant this for the next slide.

Ask

"Why not just parallelise the scan over 64 cores?" Expected: that fixes latency (÷64) but not cost; 200 q/s still needs ~2,000 cores of work. Parallelism buys latency with hardware; an index buys it with precomputation. Both are legitimate; the second is usually cheaper at this read/write ratio.

Part 2 · 00:20–01:00

From documents to postings

Forward index vs inverted index

00:20

Say

"The forward index answers 'what is in this document?'. The inverted index answers 'which documents contain this term?'. Search needs the second; updates and deletions need the first. Production systems keep both."

Ask

"Our code keeps both. Why do we need the forward index at all?" Expected: to delete or update a document you must find its postings; without the forward index you would scan the whole vocabulary. Deletion cost = O(terms in the document) with it, O(vocabulary) without. Also: snippets, highlighting, re-ranking need the document content.

Precise claim

Query cost becomes roughly proportional to the sum of the posting-list lengths for the query terms. For rare terms that is tiny; for common terms ("the", "error") it approaches the corpus size — which is why stop words and ranking-aware early termination exist. The experiment will show exactly this gap.

Stop words: the real trade-off

Stop words make up a large share of all word occurrences in English text, so dropping them shrinks the index noticeably and removes the longest posting lists (which are the slowest to intersect). Cost: phrase queries and queries made only of stop words stop working. Modern engines often keep stop words and handle long lists with ranking-aware early termination and compression. There is no universal answer; the analyzer is a product decision.

Stemming, at the right level

Stemmers (e.g. Porter for English) apply suffix rules: fast, sometimes wrong ("university" and "universe" can collide). Lemmatisers use a dictionary: more accurate, slower, language-specific. For Arabic, root-based stemming is much more aggressive than English stemming. Do not go deeper — the point is the recall/precision trade and the re-index cost.

Ask

"In our sample docs, why does the query 'posting list' miss document 6 ('Posting lists…')?" Expected: no stemming — 'list' ≠ 'lists'. Is that a bug? It is a documented consequence of the analyzer.

Document ids

  • Posting lists are kept sorted by id — this is what makes intersection linear and compression effective
  • Monotonic id assignment turns insertion into an append

00:35

Teaching point

"Every field in a posting multiplies across billions of postings. Deciding to store positions is deciding to roughly double or triple index size to support phrase search. Is phrase search a requirement?" — requirements drive representation.

Internal vs external ids

External ids (a 36-char UUID, a URL) are large and unordered. Engines map them to dense 32-bit integers: postings become small, sorted and compressible (next part). Consequence: an id-mapping table must be maintained and must stay consistent with the index — an invariant.

Our starter's choice

Our code accepts arbitrary ids and uses sorted insertion (lower_bound + insert): correct, but O(list length) per insert when ids arrive out of order. With monotonic ids it is an append. Ask: "Who should assign ids — caller or index?" (The index, if you want the append property guaranteed.)

Boolean queries are set operations on sorted lists

// AND: linear merge of two sorted lists
std::vector<DocId> out;
std::size_t i = 0, j = 0;
while (i < a.size() && j < b.size()) {
    if (a[i] < b[j])      ++i;
    else if (b[j] < a[i]) ++j;
    else { out.push_back(a[i]); ++i; ++j; }
}
  • AND = intersection, O(|a| + |b|)
  • OR = union (merge), O(|a| + |b|)
  • AND NOT = difference
  • Multi-term AND: start with the rarest term; the result can only shrink
  • |a| ≪ |b|: gallop / skip through b → O(|a| log |b|)
AskWhy is a pure NOT query ("documents without 'error'") dangerous as an API?

Note

This slide shows the idea of TODO 1. That is intentional: the exercise is about getting it right, integrating it and measuring it, not about inventing the merge. If you prefer, show it only after the lab.

Answer to the question

A pure NOT returns almost the entire corpus: O(N) output, which is the scan again, and possibly millions of results. Most engines only allow NOT relative to a positive clause (must + must_not). Our API is search_and_not(must, must_not) for exactly this reason: the API shape prevents an expensive query.

Rarest-first

For "the AND stampede": start with "stampede" (3 postings), not "the" (millions). This needs the document frequency per term — one reason document_frequency() is public and cheap (it is the list length).

Skip pointers / galloping

When one list is tiny and the other huge, exponential search on the long list avoids reading most of it. Lucene uses skip lists inside compressed posting blocks. A conceptual mention is enough.

Ranking, just enough

Boolean matching says which documents; ranking says which first.

  • tf — how often the term occurs in the document
  • df — how many documents contain it
  • idf = log(N / df) — rare terms carry more signal
  • score(d, q) = Σ over terms (1 + log tf) · idf

BM25 refines this with length normalisation and saturation. Not today.

Engineering consequences
  • Ranking needs tf in postings and N, df at query time
  • After deletions, df and N are wrong until they are recomputed: scores drift
  • Top-k of a union can be answered without scoring every match (WAND, block-max) — the Lecture 4 lesson again

00:50

Keep it short

This is not an IR course. Students need three ideas: tf, idf, and "statistics are part of the index state and can become stale".

Stale statistics example

Lucene marks deleted documents in a bitmap; df and collection statistics still count them until segments merge. Ranking is therefore slightly wrong right after mass deletions — a deliberate trade of exactness for update speed. Ask: "Is that acceptable for a support knowledge base? For a legal e-discovery system?"

Say

"Queries got faster because we did work at write time. Every row here is part of that work, and each is paid in a different currency: memory, CPU, freshness, or engineering effort."

Update amplification

Adding one 400-word document with ~200 distinct terms touches ~200 posting lists. In-place insertion into 200 large sorted arrays is slow and fragments memory. That is why production engines do not update in place: they buffer and write immutable segments (next slide).

Incremental indexing: immutable segments

  • New documents go to an in-memory buffer
  • Refresh: buffer → small immutable segment → searchable
  • Queries search all segments and merge results
  • Delete = mark in a bitmap (a tombstone, as in L2)
  • Merge: combine small segments in the background, dropping deleted docs

01:06

Why immutable segments

  • Writes become sequential appends; no in-place edits of huge sorted arrays.
  • Readers never see a half-updated structure — concurrency becomes much simpler (readers hold a snapshot of the segment list).
  • Segments compress well and can be memory-mapped.

Costs

Query cost grows with the number of segments (merge policy bounds it), merges consume I/O and CPU in the background, deleted documents occupy space until merged, and statistics (df) include deleted docs until then. Lucene/Elasticsearch work this way; Elasticsearch's default refresh interval of 1 s is exactly the "near-real-time" freshness window.

Connect forward

Lecture 9 (persistent/versioned structures) returns to "immutability simplifies reasoning but shifts cost to storage and compaction".

01:12

Expected answers (our in-memory implementation)

  1. Immediately on return (single-threaded, no buffer). In a segment-based engine: after the next refresh — "eventually, within ~1 s". The contract must say which.
  2. Our update_document = remove + add. A concurrent reader between the two steps sees no version. We avoid this only by declaring the component single-threaded. With segments: add new version, mark old deleted, publish both in one refresh → atomic from the reader's view.
  3. In memory: a crash loses the index entirely — rebuild from the source of truth. That is a valid design, if rebuild time is acceptable (measure it!). Persistent engines use a write-ahead log (transaction log) to replay unflushed changes.
  4. No. The index is a derived view of the documents database, updated after the database commits. There is always a window where they differ. Typical contract: "search is eventually consistent; the document page reads the database".
  5. add false = id exists; remove/update false = id absent. Normal outcomes, not errors (Lecture 1).

Partial failure across systems

DB write succeeds, index update fails → search is stale for that document forever unless something re-drives it. Patterns: an outbox table / change-data-capture stream that the indexer consumes (at-least-once, so indexing must be idempotent — Lecture 8), plus a periodic reconciliation or full rebuild.

Invariants of an inverted index

  1. Every posting refers to a live document
  2. Posting lists are strictly increasing by doc id: sorted, no duplicates
  3. Forward and inverted views agree: t ∈ terms(d) ⇔ d ∈ postings(t)
  4. No empty posting lists remain in the dictionary
  5. Document metadata (lengths, N) matches the indexed set
Where bugs come from
  • Update adds new postings but forgets to remove old ones → a document matches words it no longer contains
  • Re-adding an id already present → duplicate postings, double-counted tf and df
  • Removing without the forward index → dangling postings

Ask

"Which invariant, if broken, would a user notice first? Which would nobody notice for months?" Expected: #3 violated by a stale update is visible (wrong results); #5 (N, doc lengths) silently skews ranking — nobody files a bug about slightly worse ranking. Silent degradation again (L3's B1).

Methodology first (say it before the numbers)

"Both designs answer exactly the same 48 queries, in the same shuffled order, three times. Every query is timed on its own and we report medians per query class. We also check that the answers are identical — a benchmark of two implementations that disagree measures nothing." An earlier version of this benchmark repeated three queries 100 times on the index side only; that flatters the index (hot caches) and measures a different workload from the scan. Tell students this: it is a good example of a subtle benchmark bias.

Read the table with them (50,000 documents)

  • Speedup depends on the query: ~170,000× for a rare term, ~6,900× for a common single term, ~850× for an AND of two common terms. The overall median is ~7,000×. Quote the distribution, not the best number.
  • Price: build ~64× slower than just storing the text (720 vs 11 ms); memory ~8.6× (134 vs 15.5 MB) — for these components as implemented.
  • Inside the index, common-term ANDs are ~200× slower than rare-term queries: long posting lists (Zipf). The index makes cost proportional to the lists touched, not constant.
  • Rare-term timings near 1 µs are close to timer resolution; treat them as "about 1 µs", not as precise values.

What the memory numbers do and do not say

The scan component holds only the raw text. The index component holds postings, a forward list of term strings per document and metadata, but not the text — a real system keeps the text as well (for display and re-indexing), so its total storage would be text + index. Our representation is also deliberately naive (hash map of vectors, 8-byte postings, duplicated term strings). Production indexes compress postings (delta + variable-length integers) and are often smaller than the text. Ask: "Which of these rows would compression change?" (memory yes, rare-query latency barely, build time up.)

02:28

Expected answers

  1. See the results slide; plus code complexity and new failure modes (index out of sync with the source).
  2. When the scan wins: small collections (at 500–1,000 docs the scan costs a few ms per query — acceptable for an admin page); very high write rates with rare queries (log data searched once a day → grep the files); ad-hoc queries the index cannot answer (regular expressions, substrings inside words); strict freshness requirements where any index lag is unacceptable and the data is small. Simplicity, no build cost and no synchronisation are real benefits. Asymptotic superiority does not automatically justify operational complexity.
  3. Long posting lists. Options: stop words; start with the rarest term (already done); skip lists/galloping; ranked retrieval that stops after the top-k (WAND); caching results for popular queries (L3!).
  4. Not shown: real text and query logs (Zipf synthetic only; 48 queries is a small workload), updates and deletes under load, tail latency under concurrent load (we report medians and a p90 over only 144 samples), memory after compression, the text storage a real system also needs, multi-segment behaviour, concurrency, disk-resident indexes, other machines and compilers.

Teaching point

"'Faster search' is not a result. 'a median ~7,000× faster query (from ~850× to ~170,000× depending on the query class) for ~8.6× memory and ~64× build time, at 50k documents, on synthetic data' is a result — and it comes with a list of what it does not show."

Point out the last row

"Rebuild equivalence" is the strongest test for any incrementally maintained structure: apply a long random sequence of updates, then rebuild from the final documents, and compare the two indexes (or their query results). It catches exactly the update-path bugs that example-based tests miss. It applies to many projects (caches with invalidation, materialised views, aggregates).

Summary

  1. A linear scan's cost grows with the corpus; an index makes cost proportional to the posting lists touched.
  2. The analyzer defines what "match" means and must be identical at index and query time.
  3. Sorted postings make AND/OR linear merges; start with the rarest term.
  4. The index is precomputed work: pay in memory, build time, update complexity and freshness.
  5. Immutable segments + merge make updates and concurrency manageable, at the cost of background work.
  6. Specify when changes become searchable, and what happens on partial failure.
